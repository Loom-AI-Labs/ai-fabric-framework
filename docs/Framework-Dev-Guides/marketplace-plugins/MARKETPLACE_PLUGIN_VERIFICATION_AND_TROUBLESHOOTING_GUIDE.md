## 1) Verification Principle

A plugin is only verified when all of these are true:

1. install record exists with correct status
2. entitlement state allows compilation
3. resolved deployment draft contains the contribution
4. draft validates
5. published version contains the contribution in the correct artifact
6. apply succeeds
7. release verification passes
8. runtime behavior matches the contribution

Stopping earlier than this proves only part of the path.

---

## 2) Quick Verification Flow

Use this sequence for any plugin type:

1. inspect marketplace install summary
2. inspect marketplace impact
3. resolve the install
4. fetch the deployment draft
5. validate the draft
6. publish the draft
7. apply the version
8. inspect releases and verification runs
9. inspect the published artifacts
10. run live runtime proof

## 3) Control-Plane Endpoints

- `GET /api/deployments/{deploymentId}/marketplace-installs`
- `GET /api/deployments/{deploymentId}/marketplace-impact`
- `POST /api/deployments/{deploymentId}/marketplace-installs`

## 4) What To Inspect By Plugin Type

### 4.1 `TEMPLATE`

Verify:

- a deployment was created through bootstrap
- the created deployment draft contains the expected shell and template defaults
- recommended plugins are visible as normal marketplace choices

### 4.2 `ACTION`

Verify:

- the draft `actionsConfig` contains the marketplace-managed action entries
- the effective routing artifact contains the intended routes
- explicit routing overrides still win over inline route defaults
- live action execution works

### 4.3 `DATA`

Verify:

- the draft `knowledgeSourceConfig` contains the marketplace-managed sources
- the draft `marketplaceDatasetConfig` contains the plugin datasets
- apply-time sync completed
- runtime returns attributed evidence from the plugin source

### 4.4 `INFERENCE_PROFILE`

Verify:

- the draft `providerConfig` contains the marketplace-managed provider fields
- provider connectivity is ready
- release verification confirms the inference runtime contract

## 5) Published Artifact Checks

After publish, inspect the version artifacts.

For action plugins:

- `ai-actions.yml`
- routing artifact as generated by the deployment compiler

For data plugins:

- `ai-knowledge-source-config.json`
- `ai-marketplace-dataset-config.json`
- optional `ai-entity-config.yml`

For inference-profile plugins:

- `ai-provider-config.json`

You are looking for:

- marketplace-managed ids
- expected config values
- expected secret-ref bindings
- expected shell module or card contributions

## 7) Common Errors And Meanings

### 7.1 Template plugin install rejected

Typical message:

- template plugins must be used through marketplace bootstrap flow

Meaning:

- you attempted to install a `TEMPLATE` plugin onto an existing deployment

Fix:

- use the template bootstrap API instead

### 7.2 Inference profile conflict

Typical message:

- only one inference-profile plugin may be enabled per deployment

Meaning:

- another enabled inference profile already exists

Fix:

- disable or remove the other inference profile first

### 7.3 Shared-index data source fails runtime startup

Typical message:

- shared-index knowledge source requires a shared-storage-capable vector provider

Meaning:

- the deployment vector backend cannot host the required shared dataset behavior

Fix:

- move the deployment to a shared-storage-capable vector provider or compatible managed profile

### 7.4 Draft remains unchanged after install

Likely causes:

- entitlement not active
- install not resolved
- install disabled

Fix:

- activate entitlement
- run resolve
- reload the draft

### 7.5 Draft validation fails after plugin resolution

Likely causes:

- missing required install-form values
- invalid secret refs
- incompatible deployment target or auth mode
- invalid provider endpoint profile

Fix:

- inspect validation issues
- update install config or secret refs
- resolve again

---

## 8) Recommended Investigation Order

When something breaks, use this order:

1. install summary
2. entitlement summary
3. marketplace impact
4. deployment draft
5. draft validation issues
6. published version artifacts
7. release verification output
8. runtime live behavior

This keeps debugging aligned to the actual control-plane lifecycle.

---

## 9) Production Readiness Checklist

Before calling a plugin production-ready, prove:

- manifest validates
- install flow works on a clean deployment
- live publish/apply succeeds
- release verification passes
- runtime behavior matches the intended contribution
- removal or disable flow behaves cleanly

That is the minimum standard for a real marketplace plugin, not just a valid manifest.
