## 1) Core Rule

Marketplace plugins are declarative control-plane packages.

They are not:

- runtime code plugins
- frontend code plugins
- hot-loaded modules

Every plugin must compile into a deployment-backed contract that already exists in platform and runtime.

Current public plugin types:

- `TEMPLATE`
- `ACTION`
- `DATA`
- `INFERENCE_PROFILE`

If a proposed plugin cannot compile into an existing runtime-backed contract, it should not be published as a marketplace plugin.

---

## 2) What Each Plugin Type Compiles Into

### 2.1 `TEMPLATE`

Compiles into:

- a bootstrap request that creates a normal deployment draft

Use `TEMPLATE` for:

- shell presets
- curated module defaults
- recommended plugin sets

Do not use `TEMPLATE` for:

- runtime-only toggles
- deployment installs onto existing deployments

### 2.2 `ACTION`

Compiles into:

- deployment `actionsConfig`
- effective action-routing artifact generated by the deployment compiler
- optional shell module or card fragments

Use `ACTION` for:

- business actions
- integration actions
- safe write operations with confirmation rules

### 2.3 `DATA`

Compiles into:

- deployment `knowledgeSourceConfig`
- deployment `marketplaceDatasetConfig`
- optional `entityConfig`
- optional shell fragments

Use `DATA` for:

- packaged shared knowledge
- SQL-backed sync data
- folder-backed sync data

### 2.4 `INFERENCE_PROFILE`

Compiles into:

- deployment `providerConfig`
- marketplace-managed inference metadata inside `providerConfig`

Use `INFERENCE_PROFILE` for:

- BYOK provider packages
- managed endpoint-profile packages
- bounded inference offers for orchestration, generation, and embeddings

## 3) Authoring Rules

### 3.1 Secrets

Never place raw secrets in:

- manifest JSON
- deployment draft config
- plugin catalog metadata

Use:

- install-form field type `secretRef`
- deployment install `secretRefs`

### 3.2 Compatibility

Use the compatibility block to constrain plugin usage.

Current supported compatibility axes:

- `minPlatformVersion`
- `maxPlatformVersion`
- `requiredCapabilities`
- `supportedDeploymentTargets`
- `supportedAuthModes`
- `supportedProviderModes`

### 3.3 Permissions

Permissions must reflect actual contributions.

Examples:

- action contributions require `permissions.contributesActions = true`
- data contributions require `permissions.contributesKnowledgeSources = true`
- inference contributions require `permissions.contributesProviders = true`
- shell fragments require `permissions.contributesShellPresentation = true`
- install-form secret refs require `permissions.requiresDeploymentSecrets = true`

### 3.4 Shell Contributions

Public plugins may influence shell behavior only through bounded shell fragments that compile into deployment `shellConfig`.

Do not design plugins that require arbitrary frontend code execution.

### 3.5 Unsupported Surfaces

Do not author public plugins for:

- arbitrary UI bundles
- arbitrary policy engines
- arbitrary analytics scripts
- arbitrary runtime code
- removed public `AUTOMATION` type

If later productization needs those surfaces, they need a new bounded runtime-backed contract first.

## 4) Manifest Structure

Every plugin version manifest is JSON with:

- `schemaVersion`
- `pluginId`
- `version`
- `pluginType`
- `displayName`
- optional descriptive metadata
- `compatibility`
- `pricing`
- optional `installForm`
- `permissions`
- `contributions`

Read the strict contract in:

- `./MARKETPLACE_PLUGIN_MANIFEST_REFERENCE.md`

---

## 5) Install Form And Secret Ref Model

Install forms describe the operator inputs required when the plugin is installed.

Supported field types:

- `text`
- `url`
- `boolean`
- `select`
- `number`
- `secretRef`

Operational split:

- static author intent belongs in the manifest
- deployment-specific values belong in install `config`
- deployment secret references belong in install `secretRefs`

Good example:

- `mkp-action-notifications`
  - `provider` in `config`
  - `credentialSecretRef` in `secretRefs`

## 7) Local Author Workflow

Recommended workflow:

1. Write the manifest.
2. Create or update a publisher record.
3. Submit the plugin version through the marketplace submission flow.
4. Run submission validation.
5. Publish the version.
6. Install it onto a non-production deployment.
7. Resolve the install into the draft.
8. Validate, publish, and apply the deployment.
9. Run plugin verification checks.

Useful routes:

- `POST /api/marketplace/publishers`
- `POST /api/marketplace/publishers/{publisherId}/submissions`
- `POST /api/marketplace/submissions/{pluginVersionId}/validate`
- `POST /api/marketplace/submissions/{pluginVersionId}/publish`

---

## 8) Live Verification Expectations

A plugin is not “done” when it validates as a manifest.

For production-ready authoring, prove:

- the install can be created
- entitlement can become active
- install resolves into the deployment draft
- draft validates cleanly
- published artifacts contain the intended contribution
- release verification passes
- runtime behavior matches the intended contract

Use:

- `scripts/verify-marketplace-install-flow.sh`

---

## 9) Common Author Mistakes

Avoid these:

- using template plugins through deployment install APIs
- defining action routes with both `url` and `path`
- omitting `datasetRef` when multiple data datasets exist
- declaring unsupported capability profiles
- omitting secret-ref permissions for install-form `secretRef` fields
- trying to enable more than one inference-profile plugin on one deployment

If in doubt, validate against the manifest reference and then verify against a real deployment install.
