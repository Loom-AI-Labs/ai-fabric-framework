# Vector Database Configuration, Auth, And Deployment Guide

This guide is the detailed operator reference for vector-backed deployments in Platform V2.

It explains:

- how vector providers are modeled in the platform
- what is stored in deployment config versus platform Secrets
- which credentials are management keys versus runtime/data-plane keys
- what `EXTERNAL_EXISTING` and `PLATFORM_MANAGED` actually mean per vendor
- how apply wires runtime and connector env from platform state
- how to verify a live deployment end to end

Related guides:

- `PLATFORM_PROVIDER_AND_VECTOR_DEPLOYMENT_GUIDE.md`
- `MANAGED_VECTOR_DATABASE_ADMINISTRATION_GUIDE.md`
- `RUNTIME_AUTHORIZATION_AND_ACCESS_CONTROL_GUIDE.md`
- `VERIFICATION_PLAYBOOK.md`

## 1. Mental Model

The platform separates vector deployment into three layers:

1. Deployment draft config
2. Platform secret store
3. Derived runtime deployment env

The operator edits layer `1`, stores credentials in layer `2`, and the platform generates layer `3` during apply.

Do not put vendor secrets into:

- draft JSON
- prompts
- actions config
- entity config
- routing config

The runtime and REST connector should receive secret references generated by the platform, not raw secret literals embedded in the draft.

## 2. Provisioning Modes

The platform uses `vectorProvisioningMode` to distinguish how a deployment gets vector storage.

### 2.1 `LOCAL_MANAGED`

Used for local runtime-managed backends such as:

- `lucene`
- `memory`

No external vendor resource is created.

### 2.2 `EXTERNAL_EXISTING`

The customer or operator already has a managed vendor endpoint or self-hosted cluster.

The platform:

- stores non-secret connection details in the deployment draft
- stores auth credentials in Secrets
- verifies connectivity
- deploys runtime against that endpoint

The platform does not create the vendor resource in this mode.

### 2.3 `PLATFORM_MANAGED`

The platform uses a vendor control plane to create, reconcile, or bind the deployment-owned vector target.

The platform:

- validates provider inputs
- uses management credentials from Secrets
- creates or reuses the vendor resource where formal APIs exist
- binds resolved endpoint and runtime credentials back into deployment state
- deploys runtime against the managed resource

## 3. Supported Provider Matrix

Current vector backend posture:

- `lucene`
  - mode: `LOCAL_MANAGED`
- `memory`
  - mode: `LOCAL_MANAGED`
  - intended for development and tests; production profiles require the explicit
    `ai.vector-db.memory.allow-in-production=true` acknowledgement
- `qdrant`
  - modes: `EXTERNAL_EXISTING`, `PLATFORM_MANAGED`
- `pinecone`
  - modes: `EXTERNAL_EXISTING`, `PLATFORM_MANAGED`
- `weaviate`
  - mode: `EXTERNAL_EXISTING`
- `milvus`
  - modes: `EXTERNAL_EXISTING`, `PLATFORM_MANAGED` through Zilliz Cloud

The platform branch has already been verified end to end against:

- Qdrant Cloud in `PLATFORM_MANAGED` using existing-cluster reuse
- Weaviate Cloud in `EXTERNAL_EXISTING`
- Pinecone in `PLATFORM_MANAGED`
- Milvus through Zilliz Cloud in `PLATFORM_MANAGED`

Important boundary:

- `weaviate` is supported as a managed-service target, but the platform does not currently create or delete Weaviate Cloud clusters because there is no equivalent public cluster lifecycle control plane exposed like Qdrant Cloud, Pinecone, and Zilliz Cloud.

## 3.1 Runtime Capability Matrix

AI Fabric keeps native vector providers as the production path because the runtime contract is broader
than simple similarity search. Providers store `entityType`, `entityId`, content, embedding, timestamps,
and metadata together, then expose lifecycle/admin operations such as exact fetch, scan, clear, counts,
and diagnostics.

The runtime advertises these capabilities through `VectorDatabaseService`:

- `supportsSearchMetadataFiltering()`: metadata filters during similarity search, preferably
  provider-side and always fail-closed for unsupported portable filters
- `supportsScanMetadataFiltering()`: metadata filters during scan/admin operations, either
  provider-native or adapter-side after exact list/scan reads, with the same fail-closed portable
  filter semantics
- `supportsExactFetchById()`: exact lookup by vector id
- `supportsClearByEntityType()`: clear one entity-type space without a caller-maintained sidecar catalog
- `supportsEfficientEntityTypeCount()`: cheap enough count by entity type for request/admin paths

`supportsEfficientEntityTypeCount()` defaults to `false`; providers must explicitly opt in only when
they use a native count/statistics path or an in-memory/local-index count that is safe for request
paths.

Current release posture:

| Provider | Search metadata filter | Scan metadata filter | Exact fetch | Clear by entity type | Efficient count | Notes |
|----------|------------------------|----------------------|-------------|----------------------|-----------------|-------|
| `lucene` | Yes, scalar metadata | Yes, scalar metadata | Yes | Yes | Yes | Local file-backed provider. Metadata filters support scalar string, boolean, integer/long, float/double values. Unsupported filter values fail closed. |
| `memory` | Yes | Yes | Yes | Yes | Yes | Dev/test only unless explicitly acknowledged for production. |
| `qdrant` | Yes | Yes | Yes | Yes | Yes | Payload indexes are expected for filtered operations. Set `ai.vector-db.operations.fail-on-missing-payload-index=true` to fail closed instead of retrying without server-side metadata filtering. |
| `pinecone` | Yes, portable scalar equality | Yes, client-side list/fetch | Yes | Yes | Yes | Search uses provider-side portable scalar metadata filters. Scan uses list/fetch with AI Fabric's portable scalar predicate and fails closed for unsupported metadata shapes. Live provider parity is covered by the opt-in `pinecone-live-tests` profile. |
| `weaviate` | Yes | Yes | Yes | Yes | Yes | Count uses native GraphQL aggregate where available, with guarded paged-scan fallback only when aggregate is unsupported. |
| `milvus` | Yes | Yes | Yes | Yes | Yes | Lifecycle uses native Milvus operations. Metadata filters are generated against stored metadata JSON and escape `LIKE` wildcard characters. Count uses native collection statistics with a scan fallback when `row_count` is not returned. |

The legacy broad `supportsMetadataFiltering()` flag remains for binary compatibility, but new platform,
governance, and admin code should use the narrower search-vs-scan capability methods.

Every provider's `adminDiagnostics()` output includes the same stable capability keys for readiness
and release checks:

- `supportsVectorScan`
- `supportsMetadataFiltering`
- `supportsSearchMetadataFiltering`
- `supportsScanMetadataFiltering`
- `supportsExactFetchById`
- `supportsClearByEntityType`
- `supportsEfficientEntityTypeCount`
- `metadataFilteredSearch`
- `metadataFilteredScan`

The same evidence is also available as a structured nested descriptor under `capabilities`. New
automation should prefer this typed descriptor and keep the flat keys only for compatibility with
older integrations. The descriptor includes:

- `providerName`
- `providerClass`
- `nativeClient`
- `supportsVectorScan`
- `supportsSearchMetadataFiltering`
- `supportsScanMetadataFiltering`
- `supportsExactFetchById`
- `supportsClearByEntityType`
- `supportsEfficientEntityTypeCount`
- `searchFilterMode`
- `scanFilterMode`
- `metadataFilterSubset`
- `entityTypeCountMode`
- `entityTypeClearMode`
- `consistencyModel`
- `durableStorage`
- `productionProfileSafe`
- `lifecycleAdminCompatible`

Provider-specific diagnostics such as namespace prefix, collection prefix, tenant handle,
payload-index strictness, payload-index readiness, scan filter mode, sparse-index detection, and local
index path are additive. Automation should use the stable keys for cross-provider gates and
provider-specific keys only for targeted checks.
Providers that support metadata filtering also expose `searchFilterMode` and `scanFilterMode` so a
release check can distinguish native provider predicates, local indexed predicates, in-memory
predicates, and adapter-side list/fetch predicates.
For Qdrant, `adminDiagnostics()` also exposes `requiredPayloadIndexFields`,
`verifiedPayloadIndexes`, `payloadIndexesSeenMissing`, `payloadIndexCreateAttempts`, and
`payloadIndexCreateFailures` from the provider's lazy first-use checks. If Qdrant reports that a
filtered search or scan needs an index and strict mode is disabled, AI Fabric creates the portable
typed indexes and retries the identical provider-filtered operation once. Diagnostics expose these
events through `payloadIndexRepairAttempts`; the legacy `metadataFilterFallbacks` key remains empty.
AI Fabric never removes the metadata filter during this retry.
The shared vector provider contract also stores the same `entityType` and `entityId` under two
independent provider scopes and proves exact fetch, entity fetch, search, scan, count, remove, and
clear operations do not cross that modeled scope.
For Pinecone, diagnostics include `searchFilterMode=provider-side-portable-scalar` and
`scanFilterMode=client-side-list-fetch-portable-scalar`, making the adapter-side scan predicate
explicit in readiness output.
For Weaviate, diagnostics include `countMode`, `aggregateCountFallbacks`, and
`aggregateCountFallbackReasons`, so aggregate-count compatibility fallback is visible per provider
class instead of being hidden behind the efficient-count capability flag. The fallback counts via
paged scan rather than a capped one-page object listing. New metadata properties use `field`
tokenization for exact matching. Search and scan also page through native results and apply the shared
exact-scalar predicate, which preserves correctness for classes created with older tokenization.
For Milvus, diagnostics include `countMode=milvus-collection-statistics-with-scan-fallback`,
`clearMode=milvus-drop-collection`, and standardized `countFallbacks` / `countFallbackReasons`.
These fields make the native statistics path visible during normal operation and make any row-count
compatibility fallback explicit in readiness output.
When AI Fabric governance wraps a vector provider, the decorator preserves the delegate provider
diagnostics and adds governance markers such as `governanceDecorated` and
`governanceCatalogWriteThrough`.
The legacy `VectorDatabase` adapter also includes these diagnostics in `getInfo()` while preserving
the older statistics fields, so older integrations can still participate in the same readiness checks.

Vector providers also emit low-cardinality Micrometer counters for fallback and retry paths:

- `ai.fabric.vector.provider.fallbacks`
  - tags: `provider`, `operation`, `reason`
  - Weaviate aggregate-count compatibility fallback:
    `provider=weaviate`, `operation=count`, `reason=aggregate_unsupported`
  - Milvus statistics response without `row_count`:
    `provider=milvus`, `operation=count`, `reason=missing_row_count`
- `ai.fabric.vector.provider.retries`
  - tags: `provider`, `operation`, `reason`
  - Qdrant typed payload-index repair:
    `provider=qdrant`, `operation=search|scan`, `reason=payload_index_repair`
  - Pinecone transient retry examples:
    `provider=pinecone`, `operation=describeindexstats`, `reason=unavailable`

These metrics intentionally do not include entity type, entity id, tenant, namespace, collection,
customer, or index tags. Use the counters for alerting and trend detection, then inspect
`adminDiagnostics()` for provider-specific scope and fallback evidence.

When `ai-fabric-web` is on the classpath and the advanced RAG controller is enabled, the runtime also
surfaces these provider diagnostics through:

```bash
curl -sS "${RUNTIME_BASE_URL}/api/ai/advanced-rag/health"
```

The response includes a `vectorDatabase` object populated from
`VectorManagementService.getProviderDiagnostics()`. This health path is intentionally lightweight: it
uses `adminDiagnostics()` and does not run vector scans, counts, or provider statistics calls. If no
`VectorManagementService` bean is available, the endpoint stays up and reports
`vectorDatabase.available=false` with `diagnosticsAvailable=false`.

When Spring Boot Actuator health is enabled, AI Fabric also registers a
`vectorProviderHealthIndicator` bean whenever `VectorManagementService` is present. It maps the same
readiness verdict to standard health:

- `UP` when `readiness.operational=true`, including `READY` and `WARN`
- `DOWN` when `readiness.status=NOT_READY`

The component can be disabled with:

```properties
management.health.ai-fabric.vector.enabled=false
```

With health details enabled, check the component through the actuator health endpoint, usually under
`/actuator/health/vectorProvider`.
For CI/release smoke verification, use the repository verifier:

```bash
RUNTIME_BASE_URL="${RUNTIME_BASE_URL}" \
.github/scripts/verify-vector-readiness-health.sh
```

By default this fails on `WARN` because `productionReady=false` is a release review item. Set
`VECTOR_READINESS_ALLOW_WARN=true` only for non-release diagnostics where operational-but-warned
runtime state is acceptable. Compatibility fallback evidence is handled separately: nonzero
`metadataFilterFallbacks`, `aggregateCountFallbacks`, `countFallbacks`, or populated fallback-reason
maps fail the verifier unless `VECTOR_READINESS_ALLOW_FALLBACKS=true` is set for an explicitly
accepted release exception. Qdrant auto-repair is not a weaker fallback; nonzero
`payloadIndexRepairAttempts` produces readiness warning evidence for operator review.

The same object includes a `readiness` verdict:

- `status=READY`: required lifecycle/admin capabilities are present and no provider warnings are active
- `status=WARN`: the provider is operational, but release checks should review warning evidence such
  as non-durable memory storage, compatibility fallback use from any provider, Pinecone clear
  consistency mode, or Qdrant payload-index auto-repair activity
- `status=NOT_READY`: diagnostics are unavailable or required lifecycle/admin capabilities are missing,
  or provider drift such as missing/failed Qdrant payload-index creation is visible

`readiness.operational` is `false` only for `NOT_READY`. `readiness.productionReady` is `true` only for
`READY`, so release automation can distinguish "usable with warnings" from "clean production-ready".

Paged scan projection flags have the same response contract across providers. When
`VectorScanRequest.includeContent`, `includeEmbedding`, or `includeMetadata` is `false`, the omitted
`VectorRecord` field is returned as `null`. Providers must not substitute empty lists or empty maps,
because an empty value is valid data and should remain distinguishable from an intentionally
suppressed field.

## 3.2 Normalized Metadata Filter Subset

For portable runtime filtering, keep metadata filters to exact equality on scalar values:

- `String`, including empty strings
- `Boolean`
- integer and long numbers

Avoid arrays, nested objects, ranges, decimal exact equality, provider-specific expressions, and
null-as-filter semantics in portable code. Providers may support richer native filters internally,
but release-safe shared paths should assume this normalized subset. If a provider cannot translate
a filter safely, it must fail closed or return no matches rather than broadening the result set.
Integral filters are exact integral filters: `rank=7` must not match decimal metadata values such as
`7.0` or `7.9` through numeric truncation.

The shared runtime helper for this rule is `VectorMetadataFilterSupport`. Providers should validate
portable filters before creating provider-native filter objects. Unsupported shapes must become an
impossible/no-match provider filter, not a dropped condition.

## 4. Secret Boundaries

This is the most important separation to keep correct.

Full reference:

- [PLATFORM_CREDENTIALS_AND_SECRET_BOUNDARIES_GUIDE.md](../security-auth/PLATFORM_CREDENTIALS_AND_SECRET_BOUNDARIES_GUIDE.md)

### 4.1 Platform operation secrets

These are used by the platform control plane itself.

Examples:

- `PLATFORM_ARTIFACT_SIGNING_KEY`
- `RAILWAY_API_TOKEN`
- `RAILWAY_WORKSPACE_ID`

They do not belong to a deployment draft.

Important split:

- `PLATFORM_ARTIFACT_SIGNING_KEY` may be stored in platform `Secrets` or platform env
- `RAILWAY_API_TOKEN` and `RAILWAY_WORKSPACE_ID` belong on the platform backend Railway service as env vars

### 4.2 Runtime and connector auth secrets

These protect the deployed runtime and REST connector.

Examples:

- `CONNECTOR_API_KEY`
- `ACTIONS_CONNECTOR_API_KEY`
- `APP_ADMIN_API_KEY`

These are shared deployment-operation credentials, but they still belong in the platform secret store, not in draft JSON.

### 4.3 Vendor management credentials

These are used by the platform when the platform is creating or reconciling vendor resources.

Examples:

- `QDRANT_CLOUD_MANAGEMENT_API_KEY`
- `PINECONE_API_KEY`
- `ZILLIZ_CLOUD_API_KEY`

These are control-plane credentials.

### 4.4 Vendor runtime/data-plane credentials

These are used by the deployed runtime against the vendor service after apply.

Examples:

- `QDRANT_API_KEY`
- `WEAVIATE_API_KEY`
- `MILVUS_USERNAME`
- `MILVUS_PASSWORD`

For some vendors the same API key material is used for both control plane and runtime access. That is a vendor limitation, not a reason to store it in the draft.

For Zilliz-backed `PLATFORM_MANAGED` Milvus deployments, the platform also creates deployment-owned managed runtime secrets for the resolved Milvus username and password after apply.

## 5. Provider-Specific Configuration

## 5.1 Weaviate Cloud

Recommended when:

- the user already has a Weaviate Cloud cluster
- the user wants a managed-service endpoint without platform-created infrastructure

Use:

- `vectorStrategy = weaviate`
- `vectorProvisioningMode = EXTERNAL_EXISTING`

Draft fields:

- `weaviateScheme`
- `weaviateHost`
- `weaviatePort`
- optional timeouts and consistency-related settings

Secrets:

- `WEAVIATE_API_KEY` when the cluster requires auth

What apply does:

- validates draft config
- verifies readiness during release checks
- compiles runtime env:
  - `AI_VECTOR_DB_TYPE=weaviate`
  - `AI_PROVIDERS_WEAVIATE_*`
- deploys runtime against the provided Weaviate endpoint

What apply does not do:

- create the Weaviate Cloud cluster
- delete the Weaviate Cloud cluster

Typical values:

- `weaviateScheme = https`
- `weaviateHost = <cluster>.weaviate.cloud`
- `weaviatePort = 443`

## 5.2 Qdrant External Existing

Use:

- `vectorStrategy = qdrant`
- `vectorProvisioningMode = EXTERNAL_EXISTING`

Draft fields:

- `qdrantHost`
- optional `qdrantPort`
- optional `qdrantGrpcPort`
- optional `qdrantPreferGrpc`
- optional `qdrantTimeout`
- optional `qdrantManagedCollectionsEnabled`

Secrets:

- `QDRANT_API_KEY` if the cluster is protected

What apply does:

- validates endpoint inputs
- verifies connectivity
- binds runtime to the provided cluster
- optionally reconciles collections if `qdrantManagedCollectionsEnabled = true`

What apply does not do:

- create the Qdrant Cloud cluster

## 5.3 Qdrant Cloud Platform-Managed

Use:

- `vectorStrategy = qdrant`
- `vectorProvisioningMode = PLATFORM_MANAGED`

Draft fields:

- `qdrantCloudProviderId`
- `qdrantCloudRegionId`
- optional `qdrantCloudAccountId`
- optional `qdrantCloudPackageId`
- optional `qdrantCloudClusterNameOverride`

Secrets:

- `QDRANT_CLOUD_MANAGEMENT_API_KEY`
- optional `QDRANT_API_KEY` for existing protected clusters

What apply does:

- uses the Qdrant Cloud control plane
- creates or reuses the cluster for the deployment
- creates deployment-scoped runtime credentials where applicable
- resolves the final cluster endpoint
- provisions collections from configured entity types

Operational note:

- if the Qdrant Cloud account cannot create new clusters because vendor billing is missing or outdated, the platform can still complete a managed deployment by reusing a named existing cluster and issuing a deployment-scoped database API key for runtime access

## 5.4 Pinecone External Existing

- `pineconeRegion`

Secrets:

- `PINECONE_API_KEY`

- validates the selected Pinecone target

## 6. How Apply Uses Platform State

When the operator clicks apply:

1. The platform validates the draft and secrets.
2. The platform publishes immutable config artifacts.
3. The platform runs provider and managed-vector readiness checks.
4. The platform provisions or reconciles vendor resources where `PLATFORM_MANAGED` is enabled.
5. The platform compiles runtime and connector env.
6. The platform applies the Railway rollout.
7. The platform verifies the live deployment.

For vector-backed deployments, the resulting runtime env normally includes:

- `AI_VECTOR_DB_TYPE`
- vendor-specific `AI_PROVIDERS_*`
- `AI_CONFIG_DEFAULT_FILE`
- `AI_ACTIONS_CATALOG_PATH`
- `AI_PROMPTS_DEPLOYMENT_CONFIG_FILE`
- runtime auth/admin settings

## 7. Auth Model During Live Operation

There are three different auth paths during live operation.

### 7.1 Connector ingress auth

This protects REST connector data-sync and action endpoints.

Typical header:

- `X-AIFABRIC-API-KEY`

Typical secret:

- `CONNECTOR_API_KEY`

### 7.2 Runtime admin auth

This protects runtime and connector `/api/admin/*` endpoints.

Typical header:

- `X-ADMIN-API-KEY`

Typical secret:

- `APP_ADMIN_API_KEY`

### 7.3 Runtime-to-connector auth

This is used when runtime calls the connector internally.

Typical secret:

- `ACTIONS_CONNECTOR_API_KEY`

These three credentials are distinct from the vendor database credentials.

## 8. Recommended Operator Workflow

1. Create the deployment from a preset or `Custom / Start from scratch`.
2. In `Providers`, choose the vector backend and provisioning mode.
3. Fill only non-secret provider details in the draft.
4. Add required vendor credentials in `Secrets`.
5. If using platform-managed external vector provisioning, review the managed provisioning summary.
6. Run provider probes.
7. Publish the version.
8. Apply the version.
9. Review release verification and runtime admin overview.
10. Run the live vector roundtrip verification script.

## 9. End-To-End Verification

Use the dedicated vector verification script:

- `scripts/verify-vector-deployment.sh`

It verifies:

- REST connector and runtime health
- REST connector admin and runtime admin endpoints
- configured vector spaces
- runtime indexing overview and vector backend type
- live upsert/delete roundtrip through the deployed REST connector
- optional platform alignment for release state and artifact URLs

For Pinecone provider-level verification before a release, also run:

```bash
cd ai-infrastructure-module
PINECONE_API_KEY=... \
PINECONE_API_HOST=https://<index-host>.pinecone.io \
PINECONE_INDEX_NAME=<index-name> \
PINECONE_LIVE_REQUIRED=true \
mvn verify -Ppinecone-live-tests -pl victor-databases/ai-fabric-vector-pinecone -am
```

This validates the native Pinecone adapter directly, including metadata-filtered search, exact fetch,
update, deterministic clear visibility, and sparse-index roundtrip behavior when the live index is
sparse. Without `PINECONE_LIVE_REQUIRED=true`, missing Pinecone credentials or location configuration
skip the live tests for local developer convenience. Keep it enabled in release gates so missing live
configuration is a failure, not a false green.

## 10. Troubleshooting

### 10.1 Release blocked before Railway apply

Check:

- provider fields are complete
- required secrets exist in platform Secrets
- platform preflight is passing

### 10.2 Runtime admin overview shows the wrong artifact URLs

Check:

- the latest release actually reached `APPLIED_VERIFIED`
- the deployment was reapplied after draft changes
- the runtime is serving the latest published version rather than the previous deployment

### 10.3 Vector count does not change after upsert

Check:

- `REST_CONNECTOR_BASE_URL` is the live connector URL
- `RUNTIME_BASE_URL` is the live runtime URL
- connector ingress auth key is correct
- runtime admin auth key is correct
- the selected vector space exists in `Entities`
- embeddings are configured and the embedding provider secret exists

### 10.4 Upsert returns `ACCESS_DENIED`

Check:

- runtime authz mode for the deployment
- connector and runtime auth headers
- the configured upstream authz target if `REMOTE_HTTP` is enabled

### 10.5 Managed vendor provisioning looks ready, but apply still fails

Check:

- the vendor management key is the correct key type
- the key has the required control-plane permissions
- the selected project/account/region/plan ids are valid for that vendor tenant

## 11. Current Boundaries

Current platform posture:

- Qdrant Cloud: formal managed control-plane support
- Pinecone: formal managed control-plane support
- Zilliz Cloud / Milvus: formal managed control-plane support
- Weaviate Cloud: external-existing managed-service target, not platform-created infrastructure

That means the platform already supports easy managed-service onboarding across the main external vector providers, but only the vendors with formal public control planes are currently platform-created and platform-cleaned up.
