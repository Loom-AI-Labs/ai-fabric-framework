# Vector Database Configuration, Auth, And Deployment Guide

This guide is the detailed operator reference for vector-backed deployments in Platform V2.

It explains:

- how vector providers are modeled in the platform
- what is stored in deployment config versus platform Secrets
- which credentials are management keys versus runtime/data-plane keys
- what `EXTERNAL_EXISTING` and `PLATFORM_MANAGED` actually mean per vendor
- how apply wires runtime and connector env from platform state
- how to verify a live deployment end to end

## 1. Mental Model

The platform separates vector deployment into three layers:

1. Deployment draft config
2. Platform secret store
3. Derived runtime deployment env

The operator edits layer `1`, stores credentials in layer `2`, and the platform generates layer `3` during apply.

Do not put vendor secrets into:

- draft JSON
- prompts
- actions config
- entity config
- routing config

The runtime and REST connector should receive secret references generated by the platform, not raw secret literals embedded in the draft.

## 2. Provisioning Modes

The platform uses `vectorProvisioningMode` to distinguish how a deployment gets vector storage.

### 2.1 `LOCAL_MANAGED`

Used for local runtime-managed backends such as:

- `lucene`
- `memory`

No external vendor resource is created.

### 2.2 `EXTERNAL_EXISTING`

The customer or operator already has a managed vendor endpoint or self-hosted cluster.

The platform:

- stores non-secret connection details in the deployment draft
- stores auth credentials in Secrets
- verifies connectivity
- deploys runtime against that endpoint

The platform does not create the vendor resource in this mode.

### 2.3 `PLATFORM_MANAGED`

The platform uses a vendor control plane to create, reconcile, or bind the deployment-owned vector target.

The platform:

- validates provider inputs
- uses management credentials from Secrets
- creates or reuses the vendor resource where formal APIs exist
- binds resolved endpoint and runtime credentials back into deployment state
- deploys runtime against the managed resource

## 3. Supported Provider Matrix

Current vector backend posture:

- `lucene`
  - mode: `LOCAL_MANAGED`
- `memory`
  - mode: `LOCAL_MANAGED`
- `qdrant`
  - modes: `EXTERNAL_EXISTING`, `PLATFORM_MANAGED`
- `pinecone`
  - modes: `EXTERNAL_EXISTING`, `PLATFORM_MANAGED`
- `weaviate`
  - mode: `EXTERNAL_EXISTING`
- `milvus`
  - modes: `EXTERNAL_EXISTING`, `PLATFORM_MANAGED` through Zilliz Cloud

The platform branch has already been verified end to end against:

- Qdrant Cloud in `PLATFORM_MANAGED` using existing-cluster reuse
- Weaviate Cloud in `EXTERNAL_EXISTING`
- Pinecone in `PLATFORM_MANAGED`
- Milvus through Zilliz Cloud in `PLATFORM_MANAGED`

Important boundary:

- `weaviate` is supported as a managed-service target, but the platform does not currently create or delete Weaviate Cloud clusters because there is no equivalent public cluster lifecycle control plane exposed like Qdrant Cloud, Pinecone, and Zilliz Cloud.

## 4. Secret Boundaries

This is the most important separation to keep correct.

Full reference:

- [PLATFORM_CREDENTIALS_AND_SECRET_BOUNDARIES_GUIDE.md](../security-auth/PLATFORM_CREDENTIALS_AND_SECRET_BOUNDARIES_GUIDE.md)

### 4.1 Platform operation secrets

These are used by the platform control plane itself.

Examples:

- `PLATFORM_ARTIFACT_SIGNING_KEY`
- `RAILWAY_API_TOKEN`
- `RAILWAY_WORKSPACE_ID`

They do not belong to a deployment draft.

Important split:

- `PLATFORM_ARTIFACT_SIGNING_KEY` may be stored in platform `Secrets` or platform env
- `RAILWAY_API_TOKEN` and `RAILWAY_WORKSPACE_ID` belong on the platform backend Railway service as env vars

### 4.2 Runtime and connector auth secrets

These protect the deployed runtime and REST connector.

Examples:

- `CONNECTOR_API_KEY`
- `ACTIONS_CONNECTOR_API_KEY`
- `APP_ADMIN_API_KEY`

These are shared deployment-operation credentials, but they still belong in the platform secret store, not in draft JSON.

### 4.3 Vendor management credentials

These are used by the platform when the platform is creating or reconciling vendor resources.

Examples:

- `QDRANT_CLOUD_MANAGEMENT_API_KEY`
- `PINECONE_API_KEY`
- `ZILLIZ_CLOUD_API_KEY`

These are control-plane credentials.

### 4.4 Vendor runtime/data-plane credentials

These are used by the deployed runtime against the vendor service after apply.

Examples:

- `QDRANT_API_KEY`
- `WEAVIATE_API_KEY`
- `MILVUS_USERNAME`
- `MILVUS_PASSWORD`

For some vendors the same API key material is used for both control plane and runtime access. That is a vendor limitation, not a reason to store it in the draft.

For Zilliz-backed `PLATFORM_MANAGED` Milvus deployments, the platform also creates deployment-owned managed runtime secrets for the resolved Milvus username and password after apply.

## 5. Provider-Specific Configuration

## 5.1 Weaviate Cloud

Recommended when:

- the user already has a Weaviate Cloud cluster
- the user wants a managed-service endpoint without platform-created infrastructure

Use:

- `vectorStrategy = weaviate`
- `vectorProvisioningMode = EXTERNAL_EXISTING`

Draft fields:

- `weaviateScheme`
- `weaviateHost`
- `weaviatePort`
- optional timeouts and consistency-related settings

Secrets:

- `WEAVIATE_API_KEY` when the cluster requires auth

What apply does:

- validates draft config
- verifies readiness during release checks
- compiles runtime env:
  - `AI_VECTOR_DB_TYPE=weaviate`
  - `AI_PROVIDERS_WEAVIATE_*`
- deploys runtime against the provided Weaviate endpoint

What apply does not do:

- create the Weaviate Cloud cluster
- delete the Weaviate Cloud cluster

Typical values:

- `weaviateScheme = https`
- `weaviateHost = <cluster>.weaviate.cloud`
- `weaviatePort = 443`

## 5.2 Qdrant External Existing

Use:

- `vectorStrategy = qdrant`
- `vectorProvisioningMode = EXTERNAL_EXISTING`

Draft fields:

- `qdrantHost`
- optional `qdrantPort`
- optional `qdrantGrpcPort`
- optional `qdrantPreferGrpc`
- optional `qdrantTimeout`
- optional `qdrantManagedCollectionsEnabled`

Secrets:

- `QDRANT_API_KEY` if the cluster is protected

What apply does:

- validates endpoint inputs
- verifies connectivity
- binds runtime to the provided cluster
- optionally reconciles collections if `qdrantManagedCollectionsEnabled = true`

What apply does not do:

- create the Qdrant Cloud cluster

## 5.3 Qdrant Cloud Platform-Managed

Use:

- `vectorStrategy = qdrant`
- `vectorProvisioningMode = PLATFORM_MANAGED`

Draft fields:

- `qdrantCloudProviderId`
- `qdrantCloudRegionId`
- optional `qdrantCloudAccountId`
- optional `qdrantCloudPackageId`
- optional `qdrantCloudClusterNameOverride`

Secrets:

- `QDRANT_CLOUD_MANAGEMENT_API_KEY`
- optional `QDRANT_API_KEY` for existing protected clusters

What apply does:

- uses the Qdrant Cloud control plane
- creates or reuses the cluster for the deployment
- creates deployment-scoped runtime credentials where applicable
- resolves the final cluster endpoint
- provisions collections from configured entity types

Operational note:

- if the Qdrant Cloud account cannot create new clusters because vendor billing is missing or outdated, the platform can still complete a managed deployment by reusing a named existing cluster and issuing a deployment-scoped database API key for runtime access

## 5.4 Pinecone External Existing

Use:

- `vectorStrategy = pinecone`
- `vectorProvisioningMode = EXTERNAL_EXISTING`

Draft fields:

- `pineconeIndexName`
- optional `pineconeApiHost`
- `pineconeCloud`
- `pineconeRegion`
- `pineconeMetric`
- deployment vector dimensions

Secrets:

- `PINECONE_API_KEY`

What apply does:

- validates the selected Pinecone target
- resolves runtime host information
- compiles Pinecone runtime env

## 5.5 Pinecone Platform-Managed

Use:

- `vectorStrategy = pinecone`
- `vectorProvisioningMode = PLATFORM_MANAGED`

Draft fields:

- `pineconeIndexName`
- `pineconeCloud`
- `pineconeRegion`
- `pineconeMetric`
- deployment vector dimensions

Secrets:

- `PINECONE_API_KEY`

What apply does:

- uses the formal Pinecone control plane
- creates or reuses the serverless index
- waits until the index is ready
- resolves the serving host
- deploys runtime against that host

## 5.6 Milvus External Existing

Use:

- `vectorStrategy = milvus`
- `vectorProvisioningMode = EXTERNAL_EXISTING`

Draft fields:

- `milvusHost`
- optional `milvusPort`
- optional `milvusDatabaseName`
- optional `milvusSecure`
- optional `milvusTimeout`

Secrets:

- optional `MILVUS_USERNAME`
- optional `MILVUS_PASSWORD`

What apply does:

- validates host/port/database configuration
- compiles runtime env for Milvus access

## 5.7 Milvus Platform-Managed Through Zilliz Cloud

Use:

- `vectorStrategy = milvus`
- `vectorProvisioningMode = PLATFORM_MANAGED`

Draft fields:

- Zilliz project / region / cluster plan inputs exposed by the `Providers` workspace

Secrets:

- `ZILLIZ_CLOUD_API_KEY`
- optional `MILVUS_USERNAME`
- optional `MILVUS_PASSWORD`

What apply does:

- uses the Zilliz Cloud control plane
- creates or reuses the deployment-owned cluster
- resolves final Milvus endpoint and connection settings
- binds runtime to the managed cluster
- creates deployment-owned managed runtime username/password secrets for the live deployment

## 6. How Apply Uses Platform State

When the operator clicks apply:

1. The platform validates the draft and secrets.
2. The platform publishes immutable config artifacts.
3. The platform runs provider and managed-vector readiness checks.
4. The platform provisions or reconciles vendor resources where `PLATFORM_MANAGED` is enabled.
5. The platform compiles runtime and connector env.
6. The platform applies the Railway rollout.
7. The platform verifies the live deployment.

For vector-backed deployments, the resulting runtime env normally includes:

- `AI_VECTOR_DB_TYPE`
- vendor-specific `AI_PROVIDERS_*`
- `AI_CONFIG_DEFAULT_FILE`
- `AI_ACTIONS_CATALOG_PATH`
- `AI_PROMPTS_DEPLOYMENT_CONFIG_FILE`
- runtime auth/admin settings

## 7. Auth Model During Live Operation

There are three different auth paths during live operation.

### 7.1 Connector ingress auth

This protects REST connector data-sync and action endpoints.

Typical header:

- `X-AIFABRIC-API-KEY`

Typical secret:

- `CONNECTOR_API_KEY`

### 7.2 Runtime admin auth

This protects runtime and connector `/api/admin/*` endpoints.

Typical header:

- `X-ADMIN-API-KEY`

Typical secret:

- `APP_ADMIN_API_KEY`

### 7.3 Runtime-to-connector auth

This is used when runtime calls the connector internally.

Typical secret:

- `ACTIONS_CONNECTOR_API_KEY`

These three credentials are distinct from the vendor database credentials.

## 8. Recommended Operator Workflow

1. Create the deployment from a preset or `Custom / Start from scratch`.
2. In `Providers`, choose the vector backend and provisioning mode.
3. Fill only non-secret provider details in the draft.
4. Add required vendor credentials in `Secrets`.
5. If using platform-managed external vector provisioning, review the managed provisioning summary.
6. Run provider probes.
7. Publish the version.
8. Apply the version.
9. Review release verification and runtime admin overview.
10. Run the live vector roundtrip verification script.

## 9. End-To-End Verification

Use the dedicated vector verification script:

- `scripts/verify-vector-deployment.sh`

It verifies:

- REST connector and runtime health
- REST connector admin and runtime admin endpoints
- configured vector spaces
- runtime indexing overview and vector backend type
- live upsert/delete roundtrip through the deployed REST connector
- optional platform alignment for release state and artifact URLs

### 9.1 Example: Weaviate Cloud external-existing

```bash
REST_CONNECTOR_BASE_URL="https://<rest>.up.railway.app" \
RUNTIME_BASE_URL="https://<runtime>.up.railway.app" \
API_KEY="<connector api key>" \
RUNTIME_ADMIN_API_KEY="<admin api key>" \
EXPECTED_VECTOR_SPACES="product" \
EXPECTED_VECTOR_DB="WeaviateVectorDatabaseService" \
PLATFORM_BASE_URL="https://<platform>.up.railway.app" \
PLATFORM_DEPLOYMENT_ID="dep-xxxxxxxx" \
PLATFORM_LOGIN_EMAIL="admin@example.com" \
PLATFORM_LOGIN_PASSWORD="<password>" \
bash ./scripts/verify-vector-deployment.sh
```

## 10. Troubleshooting

### 10.1 Release blocked before Railway apply

Check:

- provider fields are complete
- required secrets exist in platform Secrets
- platform preflight is passing

### 10.2 Runtime admin overview shows the wrong artifact URLs

Check:

- the latest release actually reached `APPLIED_VERIFIED`
- the deployment was reapplied after draft changes
- the runtime is serving the latest published version rather than the previous deployment

### 10.3 Vector count does not change after upsert

Check:

- `REST_CONNECTOR_BASE_URL` is the live connector URL
- `RUNTIME_BASE_URL` is the live runtime URL
- connector ingress auth key is correct
- runtime admin auth key is correct
- the selected vector space exists in `Entities`
- embeddings are configured and the embedding provider secret exists

### 10.4 Upsert returns `ACCESS_DENIED`

Check:

- runtime authz mode for the deployment
- connector and runtime auth headers
- the configured upstream authz target if `REMOTE_HTTP` is enabled

### 10.5 Managed vendor provisioning looks ready, but apply still fails

Check:

- the vendor management key is the correct key type
- the key has the required control-plane permissions
- the selected project/account/region/plan ids are valid for that vendor tenant

## 11. Current Boundaries

Current platform posture:

- Qdrant Cloud: formal managed control-plane support
- Pinecone: formal managed control-plane support
- Zilliz Cloud / Milvus: formal managed control-plane support
- Weaviate Cloud: external-existing managed-service target, not platform-created infrastructure

That means the platform already supports easy managed-service onboarding across the main external vector providers, but only the vendors with formal public control planes are currently platform-created and platform-cleaned up.
