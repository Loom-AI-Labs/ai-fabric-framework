## Release Recommendation

Do not merge or run the public 0.3.0 release until the blocker findings are fixed.

The PR has useful framework work and the main GitHub checks are green, but two release-process issues can produce a wrong public release:

1. The Maven Central workflow currently includes the new vector contract test module in the deploy reactor.
2. The `ai-fabric-framework-v0.3.0` tag already exists on an older commit than the PR head.

I would also fix the provider registry mismatch before release, because the public registry currently advertises provider capabilities that the Spring AI execution path does not support.

## Findings

### Blocker: Maven Central release may publish the vector contract test module

- **Files:**
  - `.github/workflows/maven-central-release.yml:85`
  - `.github/workflows/maven-central-release.yml:87`
  - `ai-infrastructure-module/pom.xml:71`
- **Evidence:** the root reactor includes `integration-Testing/vector-contract-tests`, but the Central deploy command excludes only the older integration-test modules.
- **Why it matters:** `mvn deploy` can publish `ai-fabric-vector-contract-tests` to Maven Central as part of the public framework release. The workflow already excludes other integration-test modules, so this new module looks like an accidental omission.
- **Recommended fix:** add `!integration-Testing/vector-contract-tests` to the `-pl` exclusion list in the Central release workflow. If the intent is to keep vector contracts out of normal publish/install lanes except the explicit contract job, mirror that exclusion in the relevant verify/install workflow lane too.
- **Verification note:** a local dry validation of the release profile showed `AI Fabric Vector Provider Contract Tests` inside the reactor as module 31/31.

### Blocker: the 0.3.0 release tag is already stale

- **Tag:** `ai-fabric-framework-v0.3.0`
- **Current tag target:** `93d1cf429eee9a5a6c2f4630cd81028a0466d5d4`
- **PR head reviewed:** `52ffc45c608f23a83ac2585141cb94c314cebae6`
- **Commit after the tag:** `52ffc45 Upgrade Central publishing plugin`
- **Why it matters:** a tag-based release workflow will publish the older tagged commit, not the PR head. The Central publishing plugin upgrade is outside the current tag.
- **Recommended fix:** if 0.3.0 was not published to Maven Central, recreate the tag only after the final release commit is ready. If 0.3.0 artifacts were already published or the tag was consumed externally, do not mutate the release; bump to `0.3.1` for the corrected release.

### High: provider registry advertises unsupported Spring AI capabilities

- **Files:**
  - `ai-infrastructure-module/ai-fabric-core/src/main/resources/providers-registry.yml:47`
  - `ai-infrastructure-module/ai-fabric-core/src/main/resources/providers-registry.yml:54`
  - `ai-infrastructure-module/ai-fabric-core/src/main/resources/providers-registry.yml:121`
  - `ai-infrastructure-module/ai-fabric-core/src/main/resources/providers-registry.yml:126`
  - `ai-infrastructure-module/providers/ai-fabric-provider-spring-ai/src/main/java/ai/fabric/provider/springai/SpringAiProviderFamily.java:6`
  - `ai-infrastructure-module/providers/ai-fabric-provider-spring-ai/src/main/java/ai/fabric/provider/springai/SpringAiModelResolver.java:106`
- **Evidence:** the registry marks Cohere chat as enabled and marks Anthropic embeddings as enabled, while the Spring AI provider family does not include Cohere and explicitly throws for Anthropic embeddings. The release notes say Cohere is not active and Anthropic embeddings are not supported.
- **Why it matters:** customers and validation tooling may treat the registry as the official capability map. The current state can lead to configuration that passes registry expectations but fails at runtime.
- **Recommended fix:** make the registry match executable support for 0.3.0. Suggested release-safe option: disable Cohere chat and unsupported embedding entries, or add a clear `modeledOnly`/`active: false` distinction that guards and docs understand.

### Medium: release notes read as final while the PR is still draft/open

- **File:** `docs/release-notes/0.3.0.md:3`
- **Evidence:** release notes say `Released: 2026-06-27`, name the current review branch, and pin the comparison base to `origin/main` at `1122bc6`.
- **Why it matters:** this can become stale if the PR changes before merge or if the release tag changes. It also conflicts with the stale-tag issue above.
- **Recommended fix:** mark the notes as planned/draft until the release is cut, or update the metadata after the final merge/tag. The final notes should identify the real release tag/commit.

### Low: whitespace check fails

- **Files:** `docs/Framework-Dev-Guides/LLM-guides/AI_FABRIC_FRAMEWORK_PHILOSOPHY.md`, `docs/planning/0006-framework-capability-priority-map.md`
- **Evidence:** `git diff --check origin/main...HEAD` reports trailing whitespace in both files.
- **Why it matters:** this is not a functional bug, but it is release hygiene noise and easy to prevent.
- **Recommended fix:** remove the trailing whitespace and consider adding `git diff --check origin/main...HEAD` to release guard checks.

### Non-blocking note: Spring AI action tools are currently read-first

- **Files:**
  - `ai-infrastructure-module/ai-fabric-actions-connector/src/main/java/com/ai/fabric/actions/connector/springai/AIActionToolCallbackFactory.java`
  - `ai-infrastructure-module/ai-fabric-actions-connector/src/test/java/com/ai/fabric/actions/connector/springai/AIActionToolCallbackFactoryTest.java`
- **Observation:** the tool callback path handles read-only examples well and returns confirmation requirements for guarded actions, but I did not find a completed confirmed-write execution path in the reviewed tests.
- **Recommendation:** if 0.3.0 intends provider-native Spring AI tool callbacks to execute confirmed mutating actions, add a confirmed-write test and implementation. If not, document that this provider path is read-first/confirmation-request-only and mutating governed actions should remain on the normal AI Fabric action execution path.
