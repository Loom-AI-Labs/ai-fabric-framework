# AI Fabric 0.4.0 Lifecycle Refactor Assessment

- **Assessment date:** 2026-07-25
- **Released version:** `0.4.0`
- **Release commit:** `857619fa5ad6c63abc8505448f300a8ff564522f`
- **Release tag:** `ai-fabric-framework-v0.4.0`
- **Change size:** 414 files, 20,537 insertions, and 11,272 deletions
- **Primary plan:** [Annotation-Driven Entity Lifecycle Hardening Plan](../planning/0016-annotation-entity-lifecycle-hardening-plan.md)
- **Migration guide:** [AI Entity Lifecycle Migration Guide For 0.4](../Framework-Dev-Guides/retrieval-vectorization/ANNOTATION_LIFECYCLE_0_4_MIGRATION_GUIDE.md)
- **Release notes:** [AI Fabric 0.4.0 Release Notes](../release-notes/0.4.0.md)

## Executive Verdict

Yes. The `0.4.0` work makes AI Fabric materially better as an AI enablement framework for Java.

The improvement is not the number of changed files or the addition of more annotations. The
important change is that entity synchronization now has one explicit, testable lifecycle:

```text
typed entity contract
  -> approved projection
  -> durable transaction-aware work
  -> ordered provider execution
  -> observable completion, retry, or dead letter
```

Before `0.4.0`, several public properties were descriptive but not operational, method names could
silently determine the wrong operation, full application entities could enter the queue, provider
failures could be hidden from retry workers, and rollback handling could leave source and vector
state inconsistent.

`0.4.0` replaces those behaviors instead of adding another layer around them. The result has clearer
application boundaries, safer data handling, stronger transaction semantics, one canonical
projection model, and substantially better failure evidence.

| Area | Assessment | Why |
| --- | --- | --- |
| Public contract | Major improvement | Lifecycle operations, identity, destinations, preprocessing, and strategies are typed and validated. |
| Correctness | Major improvement | Work runs after source commit, rollback produces no provider work, and stale operations cannot overwrite newer state. |
| Security and privacy | Major improvement | Only approved projections enter durable payloads; requested PII processing fails closed. |
| Operability | Major improvement | Retry, dead-letter, queue readiness, resolved contracts, and bounded metrics are visible. |
| Provider efficiency | Improvement | Each upsert performs one embedding call and one vector write. |
| Extensibility | Improvement | Custom target and identity resolvers support real application result shapes without weakening the default contract. |
| Upgrade cost | Intentional regression in compatibility | The defective `0.3.x` lifecycle and queue schema are not supported by compatibility shims. |
| Internal complexity | Higher but better owned | There are more explicit model and lifecycle types, but they replace multiple overlapping scanners and coordinators. |

## What Changed

### 1. Annotation Properties Became Runtime Contracts

[`AICapable`](../../ai-infrastructure-module/ai-fabric-core/src/main/java/ai/fabric/annotation/AICapable.java)
now requires a stable `entityType`, owns default and per-operation indexing strategies, and binds an
optional migration repository.

[`AIProcess`](../../ai-infrastructure-module/ai-fabric-core/src/main/java/ai/fabric/annotation/AIProcess.java)
now requires a typed `AIProcessOperation`. Java method names no longer imply create, update, or
delete behavior. Its optional `entityType` is an assertion rather than a second source of identity.

[`AIIdentity`](../../ai-infrastructure-module/ai-fabric-core/src/main/java/ai/fabric/annotation/AIIdentity.java)
provides an explicit identity contract for non-JPA models. JPA identities, embedded IDs, inherited
IDs, and application-supplied identity resolvers are also supported.

[`AISearchable`](../../ai-infrastructure-module/ai-fabric-core/src/main/java/ai/fabric/annotation/AISearchable.java)
and
[`AIContext`](../../ai-infrastructure-module/ai-fabric-core/src/main/java/ai/fabric/annotation/AIContext.java)
now use typed destinations and enforce preprocessing, size, priority, required-field, type, format,
and PII requirements.

`AISearchable.priority` controls projection order and retention under a character budget. It does
not pretend to alter vector similarity scores. Genuine weighted retrieval remains a separate
retrieval/ranking design concern.

**Why this is better:** a property visible to an application developer now either changes runtime
behavior or is rejected. There is less room for annotations that look meaningful but are ignored.

### 2. One Descriptor Owns The Effective Entity Contract

[`AIEntityDescriptorRegistry`](../../ai-infrastructure-module/ai-fabric-core/src/main/java/ai/fabric/indexing/descriptor/AIEntityDescriptorRegistry.java)
compiles annotations, identity, searchable fields, context fields, indexing policy, analysis policy,
migration binding, and narrowing YAML into one immutable
[`AIEntityDescriptor`](../../ai-infrastructure-module/ai-fabric-core/src/main/java/ai/fabric/indexing/model/AIEntityDescriptor.java).

The registry:

- rejects blank or duplicate entity types;
- rejects ambiguous identity declarations;
- validates field types, formats, destinations, priorities, and sanitization dependencies;
- permits configuration to narrow annotation destinations but never widen them;
- produces a stable projection hash for payload compatibility checks;
- compiles operation-specific strategy and migration behavior once.

Startup initialization and indexing validators reject invalid contracts before application traffic
is accepted.

**Why this is better:** annotation processing, YAML resolution, migration discovery, and indexing no
longer independently reinterpret the same entity.

### 3. Projection Is Allowlisted, Destination-Specific, And Bounded

[`AIEntityProjectionService`](../../ai-infrastructure-module/ai-fabric-core/src/main/java/ai/fabric/indexing/projection/AIEntityProjectionService.java)
creates separate views for:

- semantic-search text;
- RAG context;
- vector metadata;
- LLM context;
- API response metadata.

Required fields survive projection budgeting or fail with a typed validation error. Optional fields
are retained by priority. Context values are normalized into class-free JSON shapes.

When a field requests PII sanitization, projection fails if the PII service is missing, throws,
returns empty output, or claims to redact detected PII without changing the value. Error objects do
not include raw rejected content.

The projected result is a versioned
[`AIIndexDocument`](../../ai-infrastructure-module/ai-fabric-core/src/main/java/ai/fabric/indexing/model/AIIndexDocument.java).
Its schema, descriptor hash, entity envelope, payload types, operation, and bounds are validated
before durable storage.

Delete documents contain identity and operation only. They cannot carry stale searchable text,
context, or metadata.

**Why this is better:** queue rows and provider operations receive only the approved AI-facing
projection, not the complete domain object.

### 4. Lifecycle Boundaries Are Explicit And Validated

[`AIProcessAspect`](../../ai-infrastructure-module/ai-fabric-indexing/src/main/java/ai/fabric/aspect/AIProcessAspect.java)
executes the business method first, resolves typed targets, validates entity identity, and dispatches
through the public indexing gateway.

The default resolver supports direct entities, optionals, collections, and arrays. An application
can provide `AIProcessTargetResolver` for wrappers, argument-owned targets, or void deletes without
teaching the framework about application DTOs.

[`AIProcessMethodValidator`](../../ai-infrastructure-module/ai-fabric-indexing/src/main/java/ai/fabric/aspect/AIProcessMethodValidator.java)
rejects private, static, final, non-proxyable, and self-invoked boundaries.

[`AIEntityContractValidator`](../../ai-infrastructure-module/ai-fabric-indexing/src/main/java/ai/fabric/aspect/AIEntityContractValidator.java)
rejects unsupported result shapes and mismatched entity-type assertions at startup.

An entity-level `indexing.enabled: false` policy now prevents lifecycle dispatch without failing or
rolling back the application-owned domain method.

**Why this is better:** an annotation cannot silently do nothing because Spring AOP cannot reach the
method, and a wrapper DTO cannot accidentally be indexed as a domain entity.

### 5. Indexing Became Transaction-Aware And Durable

[`DefaultAIEntityIndexingGateway`](../../ai-infrastructure-module/ai-fabric-indexing/src/main/java/ai/fabric/indexing/DefaultAIEntityIndexingGateway.java)
is the single programmatic entry point for annotation lifecycle, migration, trusted data sync, and
document adapters.

When source data and the indexing queue use the same transaction manager:

1. the source mutation and projected queue row commit together;
2. a rollback removes both and performs no provider operation;
3. provider/vector work starts only after commit;
4. a provider failure does not pretend to roll back already committed business data;
5. durable work remains available for retry or dead-letter handling.

Fresh synchronous work uses `COMMIT_PENDING`. Retry workers lease only `PENDING` work, so they cannot
steal a lifecycle operation reserved for the source request's post-commit callback. If the process
dies between commit and dispatch, cleanup releases the orphan after the configured recovery timeout
without consuming a provider retry.

[`IndexingQueueService`](../../ai-infrastructure-module/ai-fabric-indexing/src/main/java/ai/fabric/indexing/queue/IndexingQueueService.java)
validates queue envelopes, provides exclusive claims, applies bounded retry backoff, reclaims expired
leases, and moves exhausted work to dead letter with stable error codes.

**Why this is better:** `SYNC`, `ASYNC`, and `BATCH` now share one durable execution model instead of
having materially different correctness and failure behavior.

### 6. Provider Work Is Ordered And Non-Duplicated

[`IndexingWorkProcessor`](../../ai-infrastructure-module/ai-fabric-indexing/src/main/java/ai/fabric/indexing/worker/IndexingWorkProcessor.java)
maintains a durable per-entity ordering state. It rejects:

- work older than the last applied queue item;
- lower source versions that arrive later;
- stale deletes after a newer recreation;
- dependent analysis whose primary indexing operation did not complete.

The ordering tombstone remains after vector deletion so old queued work cannot recreate deleted
evidence.

[`IndexingOperationExecutor`](../../ai-infrastructure-module/ai-fabric-indexing/src/main/java/ai/fabric/indexing/worker/IndexingOperationExecutor.java)
performs exactly one embedding generation and one vector write for an upsert. Delete performs one
idempotent vector removal and no embedding call. Provider failures escape with stable retry codes.

Optional entity analysis is separate dependent work. It cannot cause a completed primary vector
upsert to be retried or represented as failed.

**Why this is better:** the framework avoids duplicate provider cost and prevents delayed queue work
from restoring stale evidence.

### 7. Other Ingress Paths Now Converge On The Same Contract

The annotation path is not the only way data enters AI Fabric. `0.4.0` moved the other supported
ingress paths onto the same projection and gateway:

- [`DataSyncEntityNormalizer`](../../ai-infrastructure-module/ai-fabric-data-sync/src/main/java/ai/fabric/datasync/normalize/DataSyncEntityNormalizer.java)
  applies request bounds and creates canonical index documents for trusted push data sync.
- [`DataSyncService`](../../ai-infrastructure-module/ai-fabric-data-sync/src/main/java/ai/fabric/datasync/service/DataSyncService.java)
  uses the indexing gateway and reports retryable, permanent, projection, access, and submission
  failures without returning false success.
- [`DataMigrationService`](../../ai-infrastructure-module/ai-fabric-migration/src/main/java/ai/fabric/migration/service/DataMigrationService.java)
  resolves the compiled entity descriptor and sends source entities through the gateway.
- [`EntityRepositoryRegistry`](../../ai-infrastructure-module/ai-fabric-migration/src/main/java/ai/fabric/migration/service/EntityRepositoryRegistry.java)
  consumes the descriptor's stable type and migration repository.
- [`SpringAiDocumentIndexingAdapter`](../../ai-infrastructure-module/ai-fabric-indexing/src/main/java/ai/fabric/indexing/document/springai/SpringAiDocumentIndexingAdapter.java)
  converts Spring AI documents into the canonical versioned payload.

Behavior persistence, relationship-query fixtures, integration entities, and repository-owned real
applications were migrated to the same annotation contract.

**Why this is better:** live sync, migration/backfill, push ingestion, and Spring AI document input
no longer create subtly different vector records.

### 8. Operations Can Inspect The Resolved Runtime

[`AIEntityIndexingEndpoint`](../../ai-infrastructure-module/ai-fabric-indexing/src/main/java/ai/fabric/indexing/observability/AIEntityIndexingEndpoint.java)
exposes sanitized descriptor, process-method, strategy, projection-hash, and queue-readiness data.

[`IndexingMetrics`](../../ai-infrastructure-module/ai-fabric-indexing/src/main/java/ai/fabric/indexing/observability/IndexingMetrics.java)
records accepted, completed, failed, retried, dead-lettered, superseded, projection-failure, and
duration signals. Tags deliberately exclude entity IDs and failure messages to keep cardinality and
data exposure bounded.

**Why this is better:** operators can determine what AI Fabric resolved and what its durable workers
are doing without exposing projected content.

## Removed Components And Preserved Functionality

The greenfield cutover removed overlapping production components rather than leaving parallel
paths.

| Removed `0.3.x` ownership | `0.4.0` replacement | Preserved or improved behavior |
| --- | --- | --- |
| `AICapableAspect` | `AIProcessAspect` plus startup validators | Explicit intercepted lifecycle with typed operations and target resolution |
| `AnnotationFieldScanner` and metadata generators | `AIEntityDescriptorRegistry` plus projection services | Search/context extraction with typed destinations and validation |
| `AICapableProcessor` | Descriptor compilation and explicit analysis work | Entity contract and optional analysis without a disconnected processor |
| `AICapabilityService` | `AIEntityIndexingGateway` plus operation executor | Upsert/delete behavior with visible failures and durable retry |
| `IndexingCoordinator`, `IndexingActionPlan`, and `IndexingStrategyResolver` | Descriptor strategy resolution plus gateway dispatch | Sync, async, and batch selection through one path |
| Full serialized application entity payload | `AIIndexDocument` | Durable class-free approved projection |
| `SpringAiIndexingDocument` | `AIIndexDocument` | Spring AI ingestion without a second queue model |

No supported create, update, delete, migration, data-sync, analysis, or document-adapter capability
was intentionally removed. The removed behavior is the accidental `0.3.x` contract: method-name
guessing, ignored properties, duplicate embedding, full-entity queueing, and weak failure handling.

The governed-action system is outside this refactor and was not replaced by the indexing lifecycle.

## Tradeoffs And Boundaries

### Breaking Upgrade

This is intentionally not source- or queue-compatible with `0.3.x`. Applications must migrate
annotations and YAML, rebuild generated vectors, and recreate old indexing queue state.

That decision is justified because AI Fabric is pre-1.0, has no known external production adopters,
and retaining the old path would preserve correctness and privacy defects. It would not be a
reasonable decision after broad external adoption without a staged migration path.

### More Explicit Types

The implementation adds descriptor, projection, work-envelope, outcome, and resolver types. That is
more internal machinery than the old scanner/coordinator path.

The added complexity is justified because the lifecycle crosses application transactions, durable
storage, providers, vector databases, retries, and security boundaries. Hiding those concerns made
the old implementation shorter but not simpler in operation.

### Not Distributed ACID

AI Fabric does not claim an atomic transaction across the application database and an external
vector provider. It guarantees durable handoff with source commit, after-commit execution, retry,
ordering, and observable failure.

A synchronous provider failure does not undo already committed business data.

### Not Implicit Repository Interception

`@AICapable` describes the AI-facing entity contract. It does not watch every Spring Data repository
write. Applications still declare a public `@AIProcess` service boundary or call
`AIEntityIndexingGateway`.

This explicit boundary is safer than hidden persistence listeners and permits application
authorization and transaction ownership to remain visible.

### Proof Coverage Is Strong But Not Universal

The release includes vector contract and readiness tests, but the post-release real-provider
lifecycle proof used Lucene, OpenAI embeddings, and OpenAI generation. It does not prove every
external vector service under live credentials in the same run.

The keyed provider matrix remains a separate operational gate for provider-specific upgrades.

## Remaining Work

The following are useful follow-ups, not reasons to reverse `0.4.0`:

1. Keep annotation and queue contracts stable and make future changes additive where possible.
2. Run the keyed external-provider lifecycle matrix after changes to queue execution, metadata
   filters, or provider adapters.
3. Complete the separate document-ingestion design in
   [planning document 0010](../planning/0010-document-indexing-core-support-plan.md); document
   chunking and manifests are not solved by entity lifecycle projection.
4. Design weighted or reranked retrieval only after a real quality case requires it. Projection
   priority should remain unrelated to similarity scoring.
5. Correct demo build metadata so `branch` reports `main` instead of `unknown`; the exact commit and
   framework version are already correct.
6. Introduce a staged compatibility policy before `1.0` or before the first external production
   adopter, whichever comes first.

## Final Assessment

`0.4.0` should be retained as the new lifecycle baseline.

The framework is better because:

- developers now declare what operation happened instead of relying on naming conventions;
- only approved data reaches embeddings, vectors, queues, LLM context, and API metadata;
- invalid contracts fail at startup or projection instead of silently drifting;
- source rollback cannot produce vector work;
- committed provider failures remain durable and observable;
- stale queued work cannot overwrite newer entity state;
- provider calls are not duplicated;
- migration, data sync, annotation processing, and document adapters share one canonical model;
- the behavior is backed by transaction tests, packaged tests, Docker tests, Maven Central consumer
  proof, and live OpenAI demo verification.

The principal cost is a breaking migration from `0.3.x`. Given the pre-1.0 stage and absence of
known external users, paying that cost now was the correct engineering decision.
