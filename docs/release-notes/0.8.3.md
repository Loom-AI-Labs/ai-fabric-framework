# AI Fabric `0.8.3`

- **Release date:** 2026-09-21
- **Maven group:** `io.github.loom-ai-labs`
- **Tag:** `ai-fabric-framework-v0.8.3`
- **Upgrade baseline:** `0.8.2`
- **Java:** 21
- **Spring Boot:** 4.1.x

AI Fabric `0.8.3` gives MCP-backed actions an explicit contract for validating logical action
parameters independently from the connector's rendered MCP tool arguments.

## Fixed

The core executable-action gate previously read `execution.mcp.requiredAnyArguments` against the
logical action parameter map. A connector can legitimately transform those logical parameters into
a different outbound payload shape, so the same field could not correctly describe both stages.

Core now reads `execution.mcp.requiredAnyParams` for its pre-execution one-of check. The
`requiredAnyArguments` field is reserved for the connector or gateway to evaluate against the final
payload after `argumentTemplate` rendering.

Example:

```yaml
execution:
  adapterType: mcp-tool
  mcp:
    requiredAnyParams: [add_items, update_items, remove_item_ids]
    requiredAnyArguments: [request.items]
    argumentTemplate:
      request:
        items: "{{params.resolved_items}}"
```

## Security Boundary

- Logical one-of validation still runs before connector execution.
- Parameter schemas, evidence-bound values, trusted hidden parameters, authorization, and
  confirmation retain their existing fail-closed behavior.
- A compatible connector independently fails closed when the rendered payload does not contain any
  meaningful configured `requiredAnyArguments` path.
- The framework does not infer trust from either one-of list.
- The implementation contains no product, commerce, Shopify, or LoomAI-specific action names.

## Migration

This is a strict current-contract correction. There is no dual interpretation or compatibility
fallback.

For each MCP action that uses a one-of gate:

1. Put logical source parameter paths in `execution.mcp.requiredAnyParams`.
2. Put rendered outbound payload paths in `execution.mcp.requiredAnyArguments`.
3. Keep both fields when the source and rendered shapes differ.
4. Revalidate and republish generated action configuration before deployment.

Actions that do not configure either one-of field require no change. No framework database or HTTP
endpoint migration is required.

## Verification

- Core regressions cover logical one-of validation and prove rendered argument paths are not
  interpreted as source parameters.
- Pipeline regressions cover confirmation-ready MCP actions with both gates present.
- Release completion requires the full framework reactor, release guards, release-profile artifact
  build, an empty-cache Maven Central consumer, and a live two-turn confirmation canary.
