# AI Fabric `0.6.0`

- **Release date:** 2026-09-14
- **Maven group:** `io.github.loom-ai-labs`
- **Tag:** `ai-fabric-framework-v0.6.0`
- **Compatibility baseline:** `0.5.3`
- **Java:** 21
- **Spring Boot:** 4.1.x
- **Primary proof:** `examples/real-apps/incident-investigation-room`

AI Fabric `0.6.0` adds bounded multi-specialist chaining for Spring Boot
applications. One application-selected manager may consult a closed set of
exact-version, read-only leaf specialists, adapt after safe projected results,
run explicitly independent workers in parallel, and synthesize one attributable
answer under deterministic budgets and durable replay.

The release is cut from one immutable source tag. Publication and deployed
canary evidence are recorded separately below so source, artifacts, and runtime
identity remain distinguishable.

## What Is New

### Bounded specialist-chain contract

`ai-fabric-execution` now provides:

- exact-version `SpecialistChainId` and immutable
  `SpecialistChainDefinition<I>` registration;
- application-owned input adapters, typed target mappers, and bounded result
  projectors;
- strict `ASK_USER`, `INVOKE_ONE`, `INVOKE_PARALLEL`, `HANDOFF`, and
  `COMPLETE` directives;
- deployment ceilings plus per-chain limits;
- synchronous execute and asynchronous submit/status/result/cancel APIs;
- safe manager, worker, parallel-group, evidence-reference, budget, replay,
  and failure traces; and
- Micrometer chain outcome, selection, model-call, parallel, replay, and
  repository metrics.

The feature is disabled by default and does not alter direct specialists,
fixed plans, standalone delegation/handoff, or the existing bounded
conversation manager.

### Centralized bounded intelligence

The manager can:

- complete without a worker;
- ask one bounded clarification question;
- invoke one approved worker;
- invoke a bounded independent group under `ALL_REQUIRED` fan-in;
- inspect only application-approved worker projections;
- adaptively invoke a second relevant worker; or
- request one terminal approved read-only handoff.

Workers remain leaves. They cannot delegate, hand off, read chain conversation
history, observe siblings, or perform writes. Every worker still traverses the
existing `AIExecutionGateway`, effective-capability intersection, provider,
RAG, read-action, grounding, validation, and authorization path.

### Exact result attribution

The manager's final `COMPLETE` directive supplies `supportingResultIds`. When
workers ran, that list must exactly match all projected worker result IDs
available to the final decision. Omitted or invented IDs fail with
`CHAIN_GROUNDING_INVALID`.

This is structural attribution over registered safe projections. It does not
use keyword matching and does not claim semantic verification of every word in
the generated message.

### Durable JDBC checkpoints

The new `SpecialistChainExecutionRepository` SPI has bounded in-memory and JDBC
implementations. Durable mode provides:

- persist-before-dispatch;
- encrypted request, checkpoint, and result payloads;
- keyed access, request, and idempotency fingerprints;
- immutable chain and manager content hashes;
- optimistic compare-and-set transitions;
- worker leases and scheduled/startup recovery;
- exact payload-checked replay across restart;
- changed-definition rejection;
- current-authority re-evaluation on resume;
- uncertain in-flight outcome reporting rather than blind rerun; and
- terminal retention cleanup that excludes active work.

Applications own the datasource and production migration. Schema initialization
inside the module is intended for tests and self-contained demos.

### Deadline, cancellation, and failure hardening

- The earliest request, chain, specialist, and deployment deadline wins.
- Manager and worker results arriving after the deadline are discarded.
- Required parallel failure cancels outstanding siblings and cannot synthesize
  a success answer.
- Thread interruption is preserved.
- Manager, worker, mapper, projector, grounding, persistence, budget, and
  recovery failures remain visible with safe reason codes.
- No deterministic route or answer fallback hides a provider failure.

### Bounded structured-output correction

`STRUCTURED_GENERATION` now makes at most two output-shape attempts by default.
A malformed, unparsable, schema-invalid, or application-validator-rejected
result may receive one fresh generation from the same approved grounding. The
correction prompt includes only a safe failure category and schema location;
it never echoes the rejected model payload. Provider call errors are not
retried by this mechanism, and exhausted attempts fail visibly.

Applications sensitive to the extra possible model call can retain the former
single-attempt behavior:

```yaml
ai:
  execution:
    output-finalization:
      max-attempts: 1
```

The supported range is `1` through `3`; the `0.6.0` default is `2`.

### Backend-owned conversation coordination

Interactive chains reuse the shared turn coordinator. The backend freezes one
approved bounded history revision, workers remain conversation-isolated, and
only the final validated user/assistant turn is recorded. The browser sends
only the newest message.

### Incident Investigation Room proof

The real app now exposes Smart Investigation as its primary flow. It proves:

- health-only worker selection;
- adaptive health then change-risk consultation;
- independent health/change parallel selection;
- clarification and completion without a worker;
- no-material-change synthesis;
- one terminal handoff;
- invented-target denial;
- required-branch failure;
- exact replay with unchanged lineage;
- async status and cancellation;
- protected JDBC state and restart recovery; and
- rejection of spoofed tenant, deployment, subject, specialist, and evidence
  fields.

The standalone Maven consumer also declares the public bounded-chain contract
directly, so an application with no framework reactor parent proves the new
IDs, definition, input mapper, worker mapper, safe projector, limits, and
closed target catalog compile from candidate artifacts.

The lower-level fixed plan, delegation, handoff, and bounded one-worker manager
labs remain available for comparison.

## Dependency And Compatibility

Applications already using `ai-fabric-execution` receive the new APIs when they
upgrade the BOM, but chains remain inactive unless explicitly enabled and
registered.

```xml
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>io.github.loom-ai-labs</groupId>
      <artifactId>ai-fabric-bom</artifactId>
      <version>0.6.0</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>
```

There is no required Spring Data JPA dependency. The default durable adapter
uses Spring JDBC when a `DataSource` is present; applications may provide their
own repository implementation.

## Opt-In Configuration

```yaml
ai:
  execution:
    specialist-chains:
      enabled: true
      durable-enabled: true
      allow-ephemeral: false
      initialize-schema: false
      max-active: 250
      max-duration: PT2M
      max-manager-decisions: 4
      max-worker-invocations: 4
      max-parallel-workers: 3
      max-invocations-per-target: 1
      max-projected-result-characters: 12000
      lease-duration: PT2M
      recovery-interval: PT30S
      recovery-batch-size: 50
      max-attempts: 3
      cleanup-enabled: true
      retention: P30D
      encryption-secret: ${AI_SPECIALIST_CHAIN_ENCRYPTION_SECRET}
      fingerprint-secret: ${AI_SPECIALIST_CHAIN_FINGERPRINT_SECRET}
```

Startup fails when durable mode has no datasource/repository or when the two
stable secrets are missing, equal, or shorter than 32 characters. Explicit
ephemeral development mode requires `durable-enabled=false` and
`allow-ephemeral=true`.

## External User Migration

Applications that do not enable chains need only upgrade and run their existing
regression suite.

Applications adopting chains must:

1. Keep each manager and worker as an exact-version registered specialist.
2. Keep managers free of RAG, actions, writes, and input continuation.
3. Keep first-release workers read-only, non-interactive, and
   conversation-isolated.
4. Register one Java `SpecialistChainDefinition` plus exact component IDs for
   its input adapter, target mappers, and target projectors.
5. Use a strict manager JSON Schema with exactly the five directive fields and
   exact target enum.
6. Build trusted execution context and choose the chain in backend code; never
   accept authority or target catalogs from request JSON.
7. Install the JDBC migration, retain stable distinct secrets, and disable
   runtime schema initialization in production.
8. Supply a stable scoped idempotency key for each logical operation.
9. Expose status, safe failure, replay, and cancellation rather than hiding
   provider or persistence failures.
10. Verify restart, changed payload, changed definition, cross-tenant access,
    deadline, required-branch failure, and exact replay before enabling traffic.
11. Review the structured-output correction budget. Keep the default of two
    attempts for bounded shape recovery, or explicitly set
    `ai.execution.output-finalization.max-attempts=1` to preserve single-call
    behavior.

See
[`BOUNDED_MULTI_SPECIALIST_CHAINS.md`](../Framework-Dev-Guides/application-patterns/BOUNDED_MULTI_SPECIALIST_CHAINS.md)
for the full API and migration guide.

## Deliberately Deferred

- recursive specialist-to-specialist transitions;
- arbitrary model-authored graphs or cycles;
- WRITE-capable chain workers;
- partial-success or best-effort parallel fan-in;
- dynamic specialist discovery;
- YAML chain manifests;
- semantic claim verification beyond exact result attribution; and
- exactly-once provider invocation.

These are not empty hooks in `0.6.0`; they are outside the released contract.
