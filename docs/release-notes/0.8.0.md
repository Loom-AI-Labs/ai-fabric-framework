# AI Fabric `0.8.0`

- **Release date:** 2026-09-21
- **Maven group:** `io.github.loom-ai-labs`
- **Tag:** `ai-fabric-framework-v0.8.0`
- **Upgrade baseline:** `0.7.1`
- **Java:** 21
- **Spring Boot:** 4.1.x
- **Spring AI:** 2.0.x document ETL bridge

AI Fabric `0.8.0` adds a deliberately small governed document-indexing core. Spring AI reads,
transforms, and splits documents; AI Fabric applies trusted-resource policy, protected metadata,
deterministic identity, canonical queue work, exact deletion, and retrieval evidence.

This is not a document-management system, crawler, or replacement for AI Fabric vector providers.

## Added

- Immutable server-side `DocumentIngestionPlan` and content-free
  `DocumentIngestionManifest` contracts.
- Deterministic source/version/chunk/entity IDs and content fingerprints.
- Allowlist-only `DocumentMetadataNormalizer` with protected AI Fabric lifecycle and tenant keys.
- Stable document warning and failure families with bounded messages.
- `DocumentIndexingQueueAdapter` over the existing durable indexing queue.
- `DocumentManifestOperations` for exact, payload-free canonical delete work.
- Configurable bounds under `ai.indexing.documents.*`.
- Conditional document auto-configuration when Spring AI document classes are present and document
  support is enabled.
- A production-shaped Document Ingestion Workbench proving bounded preview, work-status
  reconciliation, tenant evidence, new-first replacement, and exact deletion.
- A packaged deterministic lifecycle smoke at
  `.github/scripts/smoke-document-ingestion-workbench.sh`.

## Changed

- `SpringAiDocumentIndexingAdapter` now prepares plans and manifests. It no longer owns queue
  submission.
- `SpringAiDocumentIndexingOptions` now requires source version and supports tenant, visibility,
  total bounds, metadata allowlists, and correlation evidence.
- Chunk/entity identity changes from the old `springai-*` shape to versioned `aidoc-*` identities.
- Provider-specific `_springAi*` metadata is replaced with protected `_aiDocument*` metadata.
- Queue submission revalidates canonical content fingerprints, chunk identities, entity policy,
  source version, and protected metadata before accepting work.

## Operational Semantics

- Planning and preview perform no embedding, queue, vector, or Data Sync operation.
- Queue acceptance means durable acceptance only. Applications must use existing work IDs and
  `IndexingWorkQuery` before marking content active.
- Reindex is application-owned and must be new-first: index and verify the candidate, activate it,
  then delete the previous manifest by exact entity IDs.
- Failed candidate indexing must leave the previous active manifest available.
- Delete completion requires successful terminal outcomes for every exact manifest ID.
- A short old/new overlap is permitted in `0.8.0`; a framework-wide active-version retrieval filter
  remains demand-gated.

## Migration Requirements

This is an intentional greenfield correction to the incomplete pre-0.8 convenience API.

1. Drain existing document indexing work.
2. Delete old `springai-*` vectors with the old application/runtime while their exact IDs are still
   available, or use an application-owned exact cleanup process.
3. Replace adapter `enqueue(...)` calls with `plan(...)` plus
   `DocumentIndexingQueueAdapter.submit(...)`.
4. Persist the returned content-free manifest and queue work IDs.
5. Reconcile worker completion before activating a version.
6. Reindex sources to generate `aidoc-*` IDs and `_aiDocument*` metadata.
7. Update evidence projections and tests that refer to `_springAi*` keys.

There is no deprecated alias or dual-write compatibility mode. See
`docs/Framework-Dev-Guides/retrieval-vectorization/DOCUMENT_INDEXING_0_8_MIGRATION_GUIDE.md`.

LoomAI Platform should treat the BOM upgrade and document-lifecycle adoption as separate gates. See
`docs/release-notes/LOOMAI_PLATFORM_AI_FABRIC_0_8_0_UPGRADE_NOTES.md` and
`docs/Framework-Dev-Guides/retrieval-vectorization/LOOMAI_AI_FABRIC_0_8_DOCUMENT_INDEXING_MIGRATION_RUNBOOK.md`.

## Deliberately Deferred

- shared REST preview DTOs;
- a document-specific Data Sync mapper;
- remote plan serialization/signing;
- Markdown, HTML, PDF/Tika, OCR, and multimodal readers;
- remote URL crawling and managed connectors;
- framework-owned source/manifest persistence and generic reindex state machines;
- quality scorecards and provider-native bulk optimization.

These features require a concrete second consumer or representative corpus. They are not required
to prove a safe, provider-neutral document lifecycle.
