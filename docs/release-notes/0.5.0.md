# AI Fabric `0.5.0`

- **Release date:** 2026-07-30
- **Maven group:** `io.github.loom-ai-labs`
- **Tag:** `ai-fabric-framework-v0.5.0`
- **Compatibility baseline:** `0.4.0`

AI Fabric `0.5.0` adds an optional bounded execution layer for versioned,
application-selected AI specialists. It lets a Spring Boot application combine
the framework's existing retrieval, structured output, conversation, and
governed-action capabilities without giving the model control of identity,
authority, workflow topology, or side effects.

Existing orchestration applications do not need to adopt this module. The
normal `RAGOrchestrator`, action, chat-session, indexing, provider, and vector
contracts remain available.

## Highlights

### Optional specialist execution

The new `ai-fabric-execution` artifact provides:

- exact `name@version` specialist identities;
- typed Java and JSON Schema input/output contracts;
- versioned YAML or JSON specialist manifests loaded at startup;
- fail-fast validation of modes, actions, vector spaces, schemas, and limits;
- application-selected synchronous and asynchronous execution;
- trusted execution context derived by backend code;
- capability intersection across mode policy, deployment inventory,
  registered capabilities, and caller scopes;
- required grounding and safe evidence references;
- explicit provider, policy, validation, and persistence failures; and
- bounded metrics and diagnostics.

The execution module is not included transitively by `ai-fabric-starter`.
Applications add it only when they need these contracts:

```xml
<dependency>
  <groupId>io.github.loom-ai-labs</groupId>
  <artifactId>ai-fabric-execution</artifactId>
</dependency>
```

### Backend-owned interaction

Interactive specialists can use AI Fabric chat-session state while the UI sends
only the latest user message. The backend owns:

- the authenticated conversation identity;
- recent approved turns;
- one active dialogue owner;
- target and continuation state;
- pending confirmation state; and
- safe persisted assistant output.

A bounded input-wait contract lets a specialist ask for missing supported
fields and resume through typed application adapters. Input waits remain
process-local in `0.5.0`.

### Fixed, governed composition

Applications can register immutable execution structures:

- sequential read-only plans with typed step mappings;
- opt-in parallel read-only groups with `ALL_REQUIRED` fan-in;
- one-level delegation to a closed exact-version allowlist;
- one-level typed handoff to a declared successor;
- a bounded conversation manager that can ask the user, invoke one approved
  read-only worker, or complete; and
- deterministic Java aggregation and safe public projection.

The model cannot create a graph, discover arbitrary specialists, recurse,
choose unrestricted tools, or execute a write through a composed plan.

### Durable machine-owned reads

Trusted application event and scheduler adapters can submit read-only
specialist work under service or system identity. Optional JDBC state adds:

- persist-before-dispatch;
- bounded worker leases;
- startup recovery;
- scoped lookup, cancellation, and replay;
- encrypted request/result state; and
- typed terminal snapshots.

This is an at-least-once read-execution contract. It is not an exactly-once
provider-call guarantee.

### Governed writes and human review

One specialist execution may propose one registered write. AI Fabric keeps the
proposal separate from execution and requires application-owned confirmation.
Optional durable receipts provide:

- idempotent execution after confirmation;
- restart-safe replay;
- stored specialist/profile/action fingerprints;
- safe projected outcomes; and
- reconciliation against the application system of record.

Optional human review persists version-bound review tasks and delivery records.
Reviewer identity, assignment, authorization, correction, approval, rejection,
information requests, escalation, expiry, and recovery remain backend-owned.
An approved write still passes through the same governed action invoker and
receipt contract. Public review-task projections expose allowed decisions in a
stable enum order, including after JDBC reload and process restart.

### Retrieval boundary hardening

The external retrieval connector now applies the `0.4` retrieval model more
strictly:

- retrieval is limited to exact approved vector spaces;
- metadata is deny-by-default and projected through an allowlist;
- reserved and unsafe metadata cannot become model evidence;
- generated-answer content from an external source is rejected as evidence;
- source URLs pass an application-owned policy;
- evidence count and content are bounded and sanitized; and
- connector denial or invalid evidence remains visible.

`AIIndexDocument` remains the internal indexing projection used to send
application-approved content and safe metadata into a selected vector
provider. It is not a second source-of-truth entity contract.

## Application Ownership

The release preserves this boundary:

| The model may | The host application owns |
| --- | --- |
| Interpret untrusted input | Authentication and principal |
| Reason over approved evidence | Subject, tenant, and deployment |
| Produce schema-bound output | Capability registration and scopes |
| Ask for supported missing input | Domain validation and transactions |
| Select from a closed read-only catalogue | Confirmation and write execution |
| Propose one registered write | Reconciliation and public projection |

Do not accept principal, subject, tenant, deployment, scopes, specialist,
provider, vector space, action, reviewer, or authority from a public request
body.

## Storage

AI Fabric owns contracts and repositories; the application owns production
schema migration and database operations.

| State | `0.5.0` storage |
| --- | --- |
| Specialist manifests | Immutable artifact or mounted configuration |
| Specialist registry | Process memory, rebuilt at startup |
| Chat turns and normal pending actions | Configured chat-session store |
| Input waits | Process memory |
| Sequential/parallel plan state | Process memory |
| Dialogue claims and manager replay | Process memory |
| Durable read jobs | JDBC `ai_specialist_execution` |
| Governed write receipts | JDBC `ai_action_proposal_receipt` |
| Human review tasks | JDBC `ai_review_task` |
| Review deliveries | JDBC `ai_review_dispatch` |
| Vector evidence | Selected vector provider |
| Domain truth | Host application system of record |

For production JDBC use:

- manage tables with application-owned Flyway or Liquibase migrations;
- disable framework schema initialization;
- configure stable, distinct encryption and fingerprint secrets;
- verify restart, replay, lease recovery, cleanup, and key mismatch; and
- monitor queued, leased, waiting, and terminal states.

## Upgrade From `0.4.0`

For applications that do not use `ai-fabric-execution`:

1. Change the BOM to `0.5.0`.
2. Run the application's unit, integration, packaged-runtime, and provider
   smoke tests.
3. Recheck external retrieval connector metadata and URL policies if that
   module is used.
4. Deploy normally.

For applications adopting bounded specialists:

1. Complete the ordinary `0.4.0` annotation-lifecycle migration first if the
   application still uses a pre-`0.4` contract.
2. Add `ai-fabric-execution` explicitly.
3. Begin with one read-only specialist and one exact version.
4. Register every action and vector space in application code.
5. Grant exact scopes such as `specialist:account-resolver@1`,
   `action:get_account_profile`, and `vector:account-policy`.
6. Load immutable manifests with fail-fast startup validation.
7. Keep authentication and trusted-context construction outside model input.
8. Add backend conversation ownership only when multi-turn behavior is
   required.
9. Add JDBC durability only for a concrete restart/replay requirement.
10. Keep write confirmation, action execution, and system-of-record
    reconciliation in trusted application code.

## Deliberately Deferred

`0.5.0` does not provide:

- unrestricted autonomous agents;
- model-generated or recursive workflow graphs;
- arbitrary model-selected tools, endpoints, providers, or credentials;
- write-capable composed plans;
- durable plans, dialogue claims, or input waits;
- exactly-once external side effects;
- dynamic reviewer selection or model-owned approval;
- a specialist-definition database or runtime hot reload;
- tenant-authored executable manifests; or
- scripts, SQL, expressions, and arbitrary HTTP tools in manifests.

These are separate roadmap decisions, not hidden behavior in this release.
