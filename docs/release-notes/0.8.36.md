## Native Milvus Token Authentication

The Milvus provider now accepts `ai.providers.milvus.token`, including the
Spring environment equivalent `AI_PROVIDERS_MILVUS_TOKEN`. It passes the token
through the native Milvus SDK token contract, not through username/password
fields. This supports serving API keys without requiring a cluster password.

```yaml
ai:
  providers:
    milvus:
      enabled: true
      host: ${MILVUS_HOST}
      port: 443
      secure: true
      token: ${MILVUS_TOKEN}
```

Supply exactly one credential form. A configured token cannot be combined
with a nonblank username or password. Explicit blank or padded tokens are
rejected before client construction; no credential fallback is introduced.
Existing username/password and unauthenticated self-managed configuration
remain available when no token is configured.

Tokens are excluded from configuration `toString` output. SDK client-startup
errors report their class without echoing third-party diagnostic messages or
causes that may include credentials. Hosts must still protect secret storage,
logs, endpoint selection and provider-side permissions. Supplying a token
does not grant tenant isolation or reduce the token's actual provider scope.

## Scope And Verification

This is a connection-authentication patch. It does not change query routing,
prompts, model decisions, retrieval ranking, collection naming, database
selection, indexing or vector lifecycle behavior. No database migration or
vector reindex is required solely for this patch.

Verification covers the core and Milvus module tests, native SDK authorization
encoding, property binding, mixed-credential rejection, whitespace rejection,
configuration redaction and existing Milvus behavior. A metadata-only native
SDK connection using an external serving token succeeded without vector writes
or model calls. Repository release guards are part of publication verification;
the standard Maven Central workflow also runs its reactor tests while publishing.

Unrelated model-provider matrices, real-app scenario matrices and the
relationship module were not rerun for this narrow authentication change.
Source/SDK verification is not a claim that every deployed host has adopted
the new artifact; hosts must verify the packaged version and their connection.
