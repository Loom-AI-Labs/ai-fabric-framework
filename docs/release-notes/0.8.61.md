# AI Fabric Framework 0.8.61

## Internal Decision Recovery

Ordinary model-directed chat now repairs incomplete intent and source-selection
decisions within a request-shared allowance. Repairs receive the latest rejected
candidate and structural finding. If the internal decision remains unresolved,
one final model call answers from available conversation history, explicitly
attached item content and already prepared, approved evidence. It does not ask
the customer to choose an internal knowledge domain.

Defaults under `ai.orchestration.decision-recovery`:

- `enabled: true`
- `max-repair-rounds: 3` (0-10)
- `repair-admission-timeout-ms: 30000` (1000-300000)
- `final-context-answer-enabled: true`

The admission window stops new repair rounds, not an in-flight provider request.
Existing extraction call limits and provider/funding contracts still apply. The
single final-answer attempt is separate from the repair allowance; it cannot
guarantee an answer during provider failure or credit exhaustion. Disabling final
generation or cancelling a request does not start an unapproved call.

## Boundaries Preserved

The fallback does not search, call tools, execute actions or replay successful
writes. Actual write receipts and pending confirmations survive compound recovery.
Unauthorized sources, document filters and raw/unusable action output remain
excluded. Attached user content is usable context, not verified ownership or
business-action authority. Strict specialist and structured-output contracts do
not receive an incompatible prose fallback.

Recovery metadata reports rounds, safe validation findings, call timing and
whether a context answer was attempted. It contains no raw prompts, credentials
or raw action envelopes. Successful final answers remain in authorized chat
history even when earlier internal pipeline routing terminated.

## Qualification

Focused tests cover shared budgets, latest-candidate repair, source ceilings,
malformed output versus provider failure, cancellation, strict contracts,
prepared evidence, attached data, receipt retention and conversation recording.
Explicit real-provider tests combine controlled routing failures with real
Spring AI answer generation. They are opt-in, not mocked quality evidence.

The local 30-module publishable reactor reported 2,592 tests, zero failures and
zero errors; its two opt-in real-provider cases were skipped in the default run
and passed separately against an explicitly configured provider. The final
Core/chat regressions, release guards and minimal consumer are checked before
publication. The Central workflow repeats release qualification on exact source.
Hosted rollout evidence is tracked by the consuming product; publication alone
does not prove deployed adoption or perfect model-answer quality.
