# AI Fabric `0.8.32`

- **Release date:** 2026-10-13
- **Maven group:** `io.github.loom-ai-labs`
- **Tag:** `ai-fabric-framework-v0.8.32`
- **Support policy:** latest release only; mixed or parallel framework/runtime versions are unsupported
- **Java:** 21
- **Spring Boot:** 4.1.x

AI Fabric `0.8.32` adds provider-neutral conversation-control mechanics for
applications that temporarily transfer response ownership from AI to a human
channel. The framework does not provide an operator inbox, workforce routing,
or vendor adapter. Those remain host and integration-provider concerns.

## Conversation Control

- Durable conversation states cover AI-active, human-pending, human-active,
  AI-resume-pending, and closed conversations.
- Versioned, idempotent transition commands reject stale or invalid state
  changes.
- Command and participant-message retries are exact: reusing an idempotency
  identity with changed payload data fails closed.
- Participant messages support `USER`, `AI`, `HUMAN`, and `SYSTEM` roles with
  owner-scoped ordering and idempotency.
- AI turn leases bind orchestration to a control epoch. A handover transition
  invalidates an in-flight lease before an action effect and before result
  commit.
- The reference JDBC store is opt-in. Production hosts remain responsible for
  reviewed deployment-local migrations and should disable schema creation.

## Host And Channel Extensions

- `ConversationChannelGateway` defines provider-neutral dispatch and incoming
  channel events without naming a vendor or operator product.
- Opening a handover may carry a bounded host-approved transcript projection
  using `ConversationChannelMessage`; provider access to raw application
  identities or unapproved attachment content is not implied.
- `ConversationChannelMessage` provides a bounded, provider-safe transcript
  projection for operator continuity when a handover opens.
- Declarative handover-intake contracts let a host describe optional,
  purpose-bound fields without making the model an identity authority.
- `@ActionConfirmationRequired` lets trusted action code decide whether one
  invocation still needs confirmation from structured parameters and trusted
  action context. The static action must remain confirmation-enabled, and a
  missing or failing dynamic policy fails closed to confirmation required.
- Connector action metadata can mark a successful control action as
  `terminal`, preventing sibling intent execution, next-step emission, and
  post-action generation from continuing after ownership changes. Selecting
  more than one terminal action in a turn fails explicitly.
- Result-commit verification distinguishes a successful terminal control
  action from an unrelated stale turn. The terminal result that intentionally
  advanced its own control epoch may be returned, while expired leases,
  ordinary stale results, and all later effects still fail closed.
- `OrchestrationTurnGuard` is a generic host-supplied guard. The framework
  does not infer handover from phrases or route by keyword.

## Migration

Adopt the `0.8.32` BOM consistently. Hosts enabling conversation control must:

1. create reviewed control, command-idempotency, and participant-message
   tables using the schemas documented in the conversation-control guide;
2. construct the JDBC store with schema initialization disabled;
3. acquire an AI lease before orchestration and install its turn guard in the
   orchestration context;
4. route human-channel dispatch and callbacks through a separately authorized
   adapter boundary; and
5. expose control capability only when the host APIs, migration, and adapter
   are present and healthy.

Applications that do not enable the feature retain their existing behavior.
