# AI Fabric `0.8.34`

- **Release date:** 2026-10-16
- **Maven group:** `io.github.loom-ai-labs`
- **Tag:** `ai-fabric-framework-v0.8.34`
- **Support policy:** latest release only; mixed or parallel framework/runtime versions are unsupported
- **Java:** 21
- **Spring Boot:** 4.1.x

AI Fabric `0.8.34` gives controlled conversations one canonical, durable
orchestration-state boundary. Pending confirmations, action drafts, and working
targets can now share the same tenant-, deployment-, owner-, and
conversation-scoped authority record used for AI/human conversation control.
This removes the need for a host to create a shadow legacy chat session merely
to preserve orchestration state.

## Canonical Conversation State

- A host opts a controlled turn into canonical state by constructing a
  server-owned `ConversationStateBinding` from its authenticated
  conversation-control boundary. Public request fields do not enable or select
  canonical storage.
- The binding must exactly match trusted tenant and deployment identity and the
  approved conversation snapshot. A mismatch fails closed before state access.
- Canonical reads and mutations require the expected conversation-control
  epoch. State changes run under the locked control row and are rejected unless
  the conversation remains `AI_ACTIVE` at that exact epoch.
- Confirmation consumption and stack replacement use compare-and-consume or
  compare-and-set semantics. A replay, concurrent turn, or interceptor that
  changes the observed pending action cannot execute the stale confirmation.
- Legacy `chat_sessions` writes now share an owner-verified atomic mutation
  boundary, and the entity uses optimistic row versioning. A detached stale
  writer is rejected instead of restoring a consumed confirmation or
  overwriting a newer action draft.
- Target recording and seeding expose canonical-state persistence failures as
  orchestration errors. They do not silently fall back to empty or legacy
  state.
- Requests without a `ConversationStateBinding` retain the existing legacy
  chat-session stores and behavior.

## Migration

Adopt the `0.8.34` BOM consistently. Hosts using controlled conversation
handover should:

1. add an `ai_conversation_orchestration_state` table keyed by
   `(tenant_id, deployment_id, conversation_id)` with an ownership column,
   revision, JSON state, timestamp, and a cascading foreign key to
   `ai_conversation_control`;
2. construct `ConversationStateBinding` only after resolving the authenticated
   canonical conversation and acquiring the AI turn lease;
3. pass the lease control epoch as `expectedControlEpoch`; and
4. declare the migration and capability in deployment readiness before
   enabling controlled-conversation products.

Hosts that retain the legacy JPA `chat_sessions` table must also add a
non-null `BIGINT` column named `row_version`, initialized to `0` for existing
rows. Hibernate-managed development schemas create this column automatically;
production schemas should add it through an application-owned migration before
starting a `0.8.34` runtime.

The reference `JdbcConversationControlStore` creates the table when
`initializeSchema=true`. Production hosts should continue to use reviewed,
application-owned migrations and `initializeSchema=false`. No vector reindex,
prompt change, provider configuration change, or model retest is required.

## Verification

- canonical scope tests cover explicit opt-in, trusted identity matching, and
  fail-closed binding mismatches;
- JDBC tests cover owner isolation, epoch fencing, non-AI control states, and
  stale-turn mutation rejection;
- confirmation tests cover atomic consumption, replay, and stack mutation;
- recording and target-seeding tests prove state failures remain visible;
- the 30-module release reactor passed its deterministic suites with no
  failures or errors before the repository-wide release gates; and
- no real-provider gate is required because this patch changes neither prompts
  nor model-selected intent/action extraction.
