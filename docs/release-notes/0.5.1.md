# AI Fabric `0.5.1`

- **Release date:** 2026-07-30
- **Maven group:** `io.github.loom-ai-labs`
- **Tag:** `ai-fabric-framework-v0.5.1`
- **Compatibility baseline:** `0.5.0`

This patch adds the missing application-facing query boundary for durable
indexing work. It lets an application reconcile work IDs returned by Data Sync
without depending on AI Fabric queue entities or internal queue services.

## New Public Contract

Applications with `ai-fabric-indexing` active can inject:

```java
private final IndexingWorkQuery indexingWorkQuery;
```

and query the opaque work ID returned as `metadata.indexingWorkId`:

```java
Optional<IndexingWorkStatus> work =
    indexingWorkQuery.findByWorkId(indexingWorkId);
```

`IndexingWorkStatus` provides:

- work, entity, and operation identity;
- indexing strategy and public lifecycle state;
- retry count and retry limit;
- bounded error and dead-letter codes;
- correlation ID;
- request, schedule, execution, error, completion, and update timestamps; and
- centralized terminal, successful-terminal, in-progress, and
  operator-review classification.

It excludes source payloads, provider result payloads, worker ownership, and
persistence objects.

## Lifecycle Semantics

| State | Meaning | Consumer behavior |
| --- | --- | --- |
| `COMMIT_PENDING` | Queue state is still tied to transaction completion. | Wait and query again. |
| `PENDING` | Durable work is waiting for a worker or retry. | Wait and query again. |
| `PROCESSING` | A worker owns the current attempt. | Wait and query again. |
| `COMPLETED` | This work applied successfully. | Mark the dependent operation complete. |
| `SUPERSEDED` | Newer work owns the entity's final indexed state. | Treat this work as terminal and reconcile against the newer source state when required. |
| `DEAD_LETTER` | Retry policy was exhausted. | Surface a safe failure and route to operator review. |

`INDEXING_RETRYABLE` remains a non-success Data Sync response. It means the
source change was accepted and durable indexing work remains pending. Consumers
must query that work instead of blindly resubmitting or treating vector
existence as proof of update/delete completion.

## LoomAI Adoption

LoomAI can preserve its current private admin response by replacing direct
dependencies on `IndexingQueueService` and `IndexingQueueEntry` with
`IndexingWorkQuery` and `IndexingWorkStatus`.

Keep these responsibilities in LoomAI:

- the private HTTP route and response DTO;
- admin authentication and authorization;
- tenant and deployment scope checks;
- polling limits, delays, and runner state transitions; and
- application-facing error projection.

Do not add a public framework HTTP endpoint. Do not expose queue payloads. Do
not reintroduce pre-`0.4` annotation or YAML compatibility behavior. LoomAI can
move directly from its current framework version to `0.5.1`; an intermediate
`0.4.0` deployment is not required. Its migration must preserve existing
domain behavior and pass its own runtime, vectorization-runner, canary, and
full-platform readiness tests.

## Verification

The implementation is covered by:

- public lifecycle and validation unit tests;
- exhaustive internal-to-public state mapping tests;
- serialized-projection tests proving queue payloads and worker identity do not
  leak;
- Spring auto-configuration tests; and
- H2 integration coverage proving a persisted item can be queried from pending
  through completed state.
