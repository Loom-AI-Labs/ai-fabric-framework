# Bounded Read-Only Parallel Plan Implementation Plan

- **Status:** Implemented and verified; commit pin pending
- **Date:** 2026-07-30
- **Framework baseline:** AI Fabric `0.4.0`
- **Code reviewed at:** `32d5c85`
- **Prerequisite:** Plans `0001` through `0012`
- **Target:** Optional P5 agentic-enablement capability; version not assigned
- **Reference proof:** `examples/real-apps/agentic-ai-action-resolver`

## 1. Purpose

Implement the first bounded parallel specialist plan without introducing a
general graph runtime, an agent group chat, or concurrent business writes.

The first supported shape is:

```text
trusted application request
  -> one registered fixed plan
  -> one immutable source-input revision
  -> two or more independently authorized READ-only specialists
  -> bounded concurrent execution
  -> ALL_REQUIRED fan-in validation
  -> one registered deterministic Java aggregator
  -> one typed result or one visible failure
```

Parallelism is useful only when the branches are genuinely independent and a
measured latency constraint justifies the extra simultaneous model work. The
framework capability therefore remains opt-in and the reference app must
compare it with an equivalent sequential plan using the same specialists,
inputs, policies, and aggregator.

## 2. Why This Step Is Now Eligible

The portfolio verdict places parallel fan-out/fan-in last. Its prerequisites
are now present:

- exact-version specialists and independent effective-capability resolution;
- typed application-called execution;
- fixed sequential plans with registered mappers and deterministic
  aggregation;
- explicit deadlines and cancellation propagation in the specialist gateway;
- typed input waits and safe resume for sequential work;
- durable read-job and human-review boundaries where persistence is required;
- one-level delegation, handoff, interactive ownership, and an
  evidence-gated conversation manager; and
- a separate Agentic AI Action Resolver reference app.

Current code evidence:

- `ExecutionPlanDefinition` and `DefaultExecutionPlanRegistry` already provide
  immutable plan registration, exact specialist binding, dependency
  validation, WRITE rejection, duration ceilings, and content hashes.
- `DefaultAIExecutionCoordinator` already invokes every step through
  `SpecialistClient`, enforces the plan deadline, validates typed results, and
  calls only a registered Java `PlanResultAggregator`.
- `DefaultAIExecutionGateway` independently resolves authority and effective
  capabilities for every specialist invocation.
- `EphemeralPlanExecutionStore` already bounds active plan state and records
  typed checkpoints, traces, terminal results, and safe failures.
- `aiFabricExecutionTaskExecutor` is an existing bounded executor configured
  by `ai.execution.async`; parallel plans must reuse it rather than create
  unbounded threads.

These foundations make a small synchronous READ-only proof valid. They do not
make durable parallel branches, arbitrary graphs, WRITE fan-in, or general
multi-agent execution valid.

## 3. Product Proof And Sequential Control

The Agentic AI Action Resolver will expose two application-called plans:

```text
account-billing-independent-sequential@1
account-billing-independent-parallel@1
```

Both plans use:

- the same trusted demo session and account;
- the same `AccountBillingResolutionPlanRequest`;
- the same exact-version account-read specialist;
- the same exact-version billing-policy assessment specialist;
- the same branch input mappers;
- the same deterministic `AccountBillingResultAggregator`; and
- the same typed `AccountBillingResolutionPlanResult`.

The account-read branch evaluates current account readiness. The billing
branch evaluates the requested resolution type and amount. Neither branch
requires the other branch's output. Their results are combined only after both
have independently succeeded.

This gives a real sequential control rather than comparing parallel execution
with the existing dependent billing plan, whose second mapper intentionally
consumes the first step's output.

## 4. First Public Contract

### 4.1 Plan stages

Introduce a small sealed plan-stage hierarchy:

```java
public sealed interface PlanStage
    permits SpecialistPlanStep, ParallelPlanStep {
    String id();
}
```

`SpecialistPlanStep` remains the existing sequential stage and implements
`PlanStage`.

`ParallelPlanStep` contains:

- a unique group ID;
- at least two exact `SpecialistPlanStep` branches;
- `FanInPolicy.ALL_REQUIRED`; and
- an explicit positive `maximumConcurrency`.

No branch names, specialist versions, mappers, or fan-in behavior may be
generated by a model.

### 4.2 Deliberately narrow fan-in

The first enum contains only:

```text
ALL_REQUIRED
```

`QUORUM`, `BEST_EFFORT`, model-based arbitration, and model-based synthesis
remain outside this plan. Adding enum values without implementing their
failure, authority, and audit semantics is prohibited.

### 4.3 Branch attribution

Plan traces add:

- optional parallel group ID; and
- the source input revision shared by all branches.

The old sequential trace constructor remains available so existing Java
callers and tests continue to compile.

## 5. Registration And Startup Validation

`DefaultExecutionPlanRegistry` will validate the complete topology at startup.

Required checks:

1. parallel execution is explicitly enabled;
2. every top-level stage and nested branch has a unique ID;
3. a parallel group contains at least two branches;
4. branch count and `maximumConcurrency` fit the deployment ceiling;
5. the first implementation starts all branches as one bounded group, so the
   declared concurrency must cover the declared branch count;
6. every branch references an exact registered specialist;
7. every branch specialist is READ-only;
8. every mapper is registered and type-compatible;
9. branch mappers may use the plan input and outputs from earlier top-level
   stages, but cannot depend on sibling outputs;
10. every branch typed client binding is valid;
11. the final aggregator's declared dependencies are available and typed;
12. the flattened specialist count fits `maxSteps`; and
13. group topology, fan-in policy, concurrency, specialist content hashes,
    mapper identities, dependencies, and aggregator identity contribute to the
    immutable plan content hash.

Invalid plans fail application startup. The runtime must not silently convert
an invalid parallel plan into a sequential plan.

## 6. Runtime Semantics

### 6.1 Source revision

The coordinator already creates a canonical hash of the typed plan input
before execution. That hash becomes the source revision for the plan and every
parallel branch trace.

All branch inputs are mapped and type-validated before any branch is invoked.
This prevents one mapper failure from leaving a partially started group.

### 6.2 Independent execution

Every branch:

- binds through `SpecialistClientFactory`;
- enters the existing `AIExecutionGateway`;
- receives the same trusted application execution context;
- receives no conversation binding;
- resolves authority and capabilities independently;
- gets a stable child idempotency key derived from plan execution and branch
  ID; and
- cannot observe a sibling output.

The coordinator uses the existing bounded
`aiFabricExecutionTaskExecutor`. It does not create a private thread pool or
call a provider client directly.

### 6.3 Completion and failure

The coordinator collects branch completions, validates specialist identity and
typed output, and checkpoints all successful branch outputs atomically in
declared branch order.

For `ALL_REQUIRED`:

- one denied, invalid, failed, cancelled, or deadline-exceeded branch fails
  the group with attributable safe evidence;
- one `CONFIRMATION_REQUIRED` branch fails with
  `PLAN_PARALLEL_WRITE_PROPOSAL_UNSUPPORTED`;
- one `WAITING_FOR_INPUT` branch fails with
  `PLAN_PARALLEL_INPUT_WAIT_UNSUPPORTED`;
- executor rejection is visible and retryable;
- plan deadline cancels outstanding futures and returns
  `PLAN_DEADLINE_EXCEEDED`;
- thread interruption cancels outstanding futures, restores the interrupt,
  and returns `PLAN_CANCELLED`;
- no partial output reaches the final aggregator; and
- no fallback reruns the group sequentially.

Branch futures are best-effort interrupted on early terminal failure. Because
all admitted branches are READ-only, a late provider response cannot commit a
business mutation and is discarded rather than checkpointed.

### 6.4 Aggregation

After all branches succeed, the existing registered Java
`PlanResultAggregator` receives only the output IDs and types it declared.

The aggregator:

- cannot grant evidence or action authority;
- cannot inspect unrestricted provider payloads;
- cannot turn a failed branch into success;
- cannot call the model implicitly; and
- returns the one typed plan output.

## 7. Configuration

Add plan properties:

```yaml
ai:
  execution:
    plans:
      enabled: true
      parallel-enabled: false
      max-parallel-branches: 4
```

Defaults:

- `parallel-enabled=false`;
- `max-parallel-branches=4`.

The Agentic AI Action Resolver explicitly enables parallel plans with a
ceiling of two. Other applications receive no behavior change.

The shared execution executor must also have at least two worker threads for
the reference proof. Existing executor configuration remains authoritative.

## 8. Compatibility

This is an additive feature-gated extension to the unreleased
`ai-fabric-execution` plan API.

Compatibility requirements:

- existing `SpecialistPlanStep` construction remains valid;
- existing sequential plan definitions compile unchanged;
- sequential coordinator behavior, wait/resume, cancellation, traces, and
  result JSON remain covered by regression tests;
- Mode and core orchestration contracts do not change;
- direct specialist, dialogue, manager, delegation, handoff, event, review,
  receipt, and durable-job paths do not change; and
- applications without a parallel stage do not use the parallel executor
  path.

## 9. Framework Implementation Slices

### Slice 1: Contract and property boundary

- add `PlanStage`;
- make `SpecialistPlanStep` implement it;
- add `ParallelPlanStep` and `FanInPolicy`;
- update `ExecutionPlanDefinition` to hold immutable `PlanStage` values;
- add feature gate and branch ceiling properties; and
- preserve old trace construction while adding group/source attribution.

### Slice 2: Registry topology validation

- flatten specialist count;
- validate global IDs;
- validate sibling independence;
- validate read-only exact bindings;
- validate branch/group ceilings; and
- include topology in the plan hash.

### Slice 3: Bounded runtime

- inject the existing bounded execution executor;
- pre-map every branch;
- submit the declared branches;
- collect completions under the plan deadline;
- cancel outstanding futures on failure, timeout, or interruption;
- atomically checkpoint successful branch outputs;
- continue into the existing deterministic aggregator; and
- expose safe branch/group diagnostics.

### Slice 4: Reference proof

- add equivalent independent sequential and parallel plans;
- add controller/service endpoints;
- publish plan topology and content hashes in health;
- add request examples and migration-safe documentation; and
- preserve the existing dependent billing plan.

### Slice 5: Verification

- run execution tests normally;
- run the clean real-app reactor normally;
- verify packaged JAR parity;
- run both comparison plans with real OpenAI;
- compare result equivalence, branch lineage, model-call count, wall time, and
  failures; and
- record the evidence without claiming a latency win if the measurement does
  not show one.

## 10. Test Matrix

### Contract tests

- defensive branch copies;
- blank/duplicate IDs rejected;
- fewer than two branches rejected;
- invalid concurrency rejected; and
- only `ALL_REQUIRED` exists.

### Registry tests

- parallel plan rejected while disabled;
- deployment branch ceiling enforced;
- flattened step ceiling enforced;
- WRITE-capable branch rejected;
- unknown specialist/mapper rejected;
- sibling dependency rejected;
- predecessor dependency accepted;
- type mismatch rejected;
- duplicate group/branch IDs rejected;
- content hash changes for topology, concurrency, specialist content,
  mapper, or fan-in changes; and
- existing sequential definitions retain stable behavior.

### Coordinator tests

- two blocking branches overlap in time;
- both independently enter the specialist client;
- mapped inputs are prepared before invocation;
- declared output order is deterministic even when completion order differs;
- successful branches checkpoint atomically;
- one branch failure cancels/discards siblings and skips aggregation;
- identity mismatch and output type mismatch fail closed;
- confirmation and input wait are rejected visibly;
- deadline cancels outstanding work;
- interruption restores interrupt status;
- executor rejection is visible;
- branch traces carry group and common source revision;
- sequential wait/resume regressions remain green; and
- final aggregation occurs exactly once.

### Reference-app tests

- both plans use the same specialist IDs, mapper types, and aggregator;
- sequential and parallel outputs are equivalent for complete input;
- both enforce trusted demo-session identity;
- both reject unauthorized access;
- health exposes strategy, group size, concurrency, and plan hash;
- no framework/provider fallback is configured; and
- packaged runtime loads all definitions.

## 11. Real-Provider Evaluation

Use a complete billing request that requires no clarification, for example an
account-credit assessment with an amount.

Record for at least three warm runs per strategy:

- end-to-end wall time;
- each branch start and completion time;
- exact specialist IDs and invocation IDs;
- plan content hash and source revision;
- typed output equality on policy-relevant fields;
- visible provider failures;
- branch count; and
- estimated model-call multiplication.

The feature is technically complete when the safety and correctness gate
passes. It is promoted beyond experimental/reference use only if the measured
latency improvement is material enough to justify concurrent provider cost.

## 12. Explicit Non-Goals

This plan does not add:

- parallel interactive conversation owners;
- branch-to-branch messages;
- sibling output dependencies;
- parallel input-wait consolidation;
- parallel WRITE proposals or business mutations;
- `QUORUM` or `BEST_EFFORT`;
- model-based fan-in;
- dynamic graph generation;
- nested parallel groups;
- durable branch recovery;
- a scheduler, broker, or distributed workflow engine;
- LangGraph, LangChain4j, or another provider stack; or
- hidden sequential fallback.

Durable parallel work needs a separate plan because branch leases,
duplicate-safe completion, restart-safe fan-in, and persistent cancellation
are materially different from this bounded in-request proof.

## 15. Implementation Evidence

The completed implementation adds:

- sealed `PlanStage` contracts with sequential `SpecialistPlanStep` and
  bounded `ParallelPlanStep`;
- the deliberately narrow `FanInPolicy.ALL_REQUIRED`;
- disabled-by-default deployment properties;
- startup rejection for disabled, oversized, dependent, unknown,
  type-incompatible, or WRITE-capable branches;
- pre-mapped branch inputs, bounded submission through the existing
  `aiFabricExecutionTaskExecutor`, deadline-aware completion, sibling
  cancellation, and atomic all-or-none checkpointing;
- deterministic declaration-order traces with a common source revision; and
- equivalent sequential and parallel Account Resolver routes using the same
  two specialists, input mappers, and Java aggregator.

Verification completed with tests enabled:

- 24 focused contract, registry, sequential coordinator, and parallel
  coordinator tests passed;
- the framework reactor passed 1,052 tests: 5 curated-default, 677 core, 59
  chat-session, and 311 execution;
- the clean real-app reactor passed 12 shared smoke-support tests and 138
  Agentic AI Action Resolver tests;
- the executable app started from its packaged JAR and health exposed the
  expected two-branch `ALL_REQUIRED` topology;
- packaged/local `ai-fabric-core` SHA-256 was
  `b2543edcc887209513060e4ec0d4246fcfa2ecc524296bc4e79dd319ffd0c9a4`;
- packaged/local `ai-fabric-execution` SHA-256 was
  `feb2c49dad6a404aab57ca92903a6d97090da69012c2e4f99decc48fc68870b0`;
  and
- `git diff --check` passed.

Real OpenAI verification used the packaged app, `gpt-4o-mini`, the same
missing-payment session, and the same complete account-credit request for
three runs per strategy. All six runs returned `SUCCEEDED` with byte-identical
typed output:

```text
accountAssessment=BLOCKED
billingDecision=AUTO_APPROVED
expectedBillingStatus=APPROVED
automaticLimit=100
```

Every sequential run recorded no branch overlap. Every parallel run recorded
overlap, retained declaration-order traces, used distinct invocation IDs, and
reported one common source revision. Average end-to-end wall time was 15.511
seconds sequentially and 6.699 seconds in parallel for this bounded
measurement. Both strategies invoked the same two specialists; parallelism
changed scheduling, not the declared work or policy result.

This measurement demonstrates value for this pair of independent reads. It is
not a general latency guarantee, and it does not justify using parallelism
where branches are dependent or provider concurrency cost is undesirable.
